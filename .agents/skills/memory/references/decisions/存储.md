## 存储（现行；2026-09-30 表形状落定）

> 状态：**现行**，已落地并接进内核。**设计篇 `docs/architecture/storage-design.md` 是 L0 的唯一事实来源**，
> 细则以它为准；本文只记**关键判断与理由**，不复述细则。

### 一、总口径

- 已定 · **从零重设计，不背兼容包袱**：无发布、无真实用户库（`git tag` 空、`version = 0.0.1`），
  故旧落盘格式、旧目录、旧 ID 一律不必兼容。**旧库拒开**属于这一档。
- 已定 · **四层**：块 / 载体 / 多 hub / 索引库；**索引库是 hub 的组件**，不是与 hub 并列的一层。
- 已定 · **顺序：文档 → 类型与异常 → 字段 → 作者审字段 → 业务逻辑**。

### 二、ID 与指针

- 已定 · **ID 是身份证，不是裸字符串**：含两套凭证（`value_uuid` 分配形态、`value_hash` 摘要形态）
  与身份字段。两套凭证**各有其用、并存不取**：**比较用分配形态，去重用摘要形态**。
  物理坐标**不进 ID 的落盘子集**。
- 已定 · **`ID` 是给 body 用的、块与 ID 绑死**：body 持有 ID；块记录携带的是指向该 ID 的凭证。
- 已定 · **ID 管自身、载荷管指针**（修正早先的"一格两用"）：块记录的身份凭证 `value_hash`
  **恒为该记录自身载荷的摘要**——记录层的自校验就这么要求（解码时当场核对），
  故它**无法同时承载 body 的摘要**。指向 body 的凭证落在**块记录的载荷**里，
  保留键 `\x00cairn.body_ref`、内容为 `{value_uuid, value_hash}` **两套都带**
  （只带摘要时，块表里"指向哪份 body"只写得出一半）。
  指针在载荷里**不影响可重建**：顺扫读出载荷即得指针。

### 三、记录与表

- 已定 · **块面 = 两条记录**：**内容记录**（载荷即编码后的 body，身份按内容签发，故同内容只存一份）
  ＋ **块记录**（载荷是指针，身份是块自己的）；读回两条一拼。
  判据落在**载荷格式**上（保留键带不可打印前缀），故档一重建补回的块行照样认得出是块，
  **类型为空也能列举**。
- 已定 · **块记录与内容记录是两种记录，故索引要两层定位**。
- 已定 · **类型无界但只是继承层级，不是嵌套**；**类型标号不落盘**（程序给出），
  不认识的 ID 一律**降级读回**（扫描 / 重建 / 合并都靠它，一处抛错即断链）。
- 已定 · **有多少个"用 ID 绑字段的类型"，就有多少张表**：`Block` → `block`、`Body` → `body`、
  领域类 → 它自己那张表。**名字是表的坐标**，不是行里的判别列。
- 已定 · **表的形状由类型登记现算，不走"手工建表"**：类型在**定义时**登记自己
  （`__init_subclass__`），由登记现算表名与列、写进 `config/tables.yaml`，**再由那份文件建库**。
  作者的原话判据：**"手工拆的与它自动拆的有明显区别"**——代码写好了，表自然拆得出来。
  **不取"运行期扫描全书"那条路**：慢，且会把没被导入的类型悄悄漏掉。
- 已定 · **子类不继承父类的表名**：`__table__` 只认本类自己写下的那一个，
  否则子类会顶掉父类那张表，"一个类型一张表"当场垮掉。
- 已定 · **声明文件是"代码 → 文件 → 库"的中段，不是源头**：文件由代码写出、又被代码读回；
  **人是可以改它的**。写文件的口径是**只追加不覆写**，要淘汰的旧表由代码**显式点名**，不靠猜。
- 已定 · **两张表的列**：`block` = 自己的身份 ＋ 指向 body 的两列 ＋ `kind` ＋ 位置观测列 ＋ 两个时刻；
  `body` = 身份 ＋ 位置观测列（**无 `kind`**）。**内容表也存位置观测列**——
  每条载体记录都要有一行（档一、巡检、将来的压实都以盘为真源）。
  代价如实记：同一位置在两张表各有一份，两份都是同一批字节的投影。
- 已定 · **`hub` / `edge` 不由类型诞生**：`hub` 的主语是载体目录、`edge` 的主语是关系本身，
  两者都不是"用 ID 绑字段的类型"，故照旧由声明层写死。
- 未定 · **删掉类型要不要删表**：当前**只增不减**；删表属破坏性动作，须显式授权。

### 四、载体与 hub 的行为

- 已定 · **落地盘面**：定长槽（槽长随载体、写在文件头）、记录自框定（总长在最前）、
  **不设封口目录**（顺扫即可重建；目录只是优化）。
- 已定 · **hub 是无状态的一层**：目录即存在证明（判据＝带 `packs/` 的直接子目录），
  索引库里的 hub 表只是**登记**；槽长随载体走（文件头自描述），封口线每次写入按配置判，
  故 hub **不存自己那份配置**；**读路径缺目录即报错，不悄悄建空 hub 顶上**。
- 已定 · **封口不留标记**：没有封印字节、也没有封口文件，"已封口"就是"该载体达到封口线"，
  故封口是**策略判断**而非落盘状态。**活跃载体 = 有空间的最满者**——写入纪律是"写到满才换"，
  故该判据不依赖时间戳与名字顺序，封口线调大后仍只有唯一答案。
  **单条记录大于封口线时照样完整写入**（否则大记录永远写不进去）。
- 已定 · **载体名取随机串**（无语义、无顺序号）：序号名在压实之后会被重用，
  而重用的名字会让**过期的索引行指向另一个文件**；随机名只会指向不存在的文件，**坏得看得见**。
- 已定 · **多 hub 的价值是确定性路径查询**：物理多 hub、引擎视角一块盘，
  查询就是"先查 hub、再按槽区间读块"——**两跳都是查表**。
  故 **hub 上名称或 ID 没有区别**：hub 名就是目录名，取人话（`main`）或取 ID 形态对查询无影响；
  hub 本身**不持有 ID**（ID 是 body 的身份证，hub 是容器）。

### 五、维护：重建、巡检、处置

- 已定 · **重建分两种口径**：**档一重建 = 只补缺行**（已有行不动）——
  因为 `kind` 与落盘时刻不在记录头里，清空重扫会**抹掉类型信息**；权威重建待 ID 专项裁定。
- 已定 · **巡检只报告、处置只补不删**：`patrol()` 把索引与真源两头对齐，发现按"可否由重建修复"分类；
  `repair()` 只动可修复的那部分——**内容没了、hub 没了、载体坏了一律不碰**
  （删行等于把"丢了东西"抹掉）。
- 已定 · **坏点即停属于重建、不属于巡检**：重建拿半份结果不能当结果；巡检要接着看完。
- 已定 · **索引库的可重建是逐表性质**：内核态可扫载体重建；领域态含真源在库内的表，
  损坏即**永久损失**，故**备份是必需能力**。
- 已定 · **表声明进配置，源码内不得出现建表 SQL**；只允许加、**破坏性变更拒绝启动**；
  建表只在开库 / 挂载，**不在热路径**。

### 六、已知缺口与未来项

- 待裁 · **摘块与巡检的相互作用**：`drop` 只摘行、记录留在载体里（追加写不动旧字节），
  于是巡检把块记录报成 `missing_row`、处置又把它补回来（等于撤销摘块）。
  消掉它要么引入墓碑，要么等压实回收落地——两条都属未来项。
- 未来项 · **合并与短命 hub**（作者：短期不做）：并发承接 + 合并回主 hub + 销毁；
  同 ID 冲突按 `birth_time` 裁决。"合并期 hub 归属改写"随之推后。
- 未来项 · **压实回收**：删内容要判引用（同内容可能还有别的块在用）。
- 未定 · **列举仍会读全库正文**：去掉它要先把"块记录判据落成索引里的一列"，
  属设计篇 §12 的字段问题，**待作者裁**。
