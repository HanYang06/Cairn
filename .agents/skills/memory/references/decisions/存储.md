## 存储（现行；2026-10-02 值范式整条落地）

> 状态：**现行**，已落地并接进内核。**设计篇 `docs/architecture/storage-design.md` 是 L0 的唯一事实来源**，
> 细则以它为准；本文只记**关键判断与理由**，不复述细则。

### 一、总口径

- 已定 · **从零重设计，不背兼容包袱**：无发布、无真实用户库（`git tag` 空、`version = 0.0.1`），
  故旧落盘格式、旧目录、旧 ID 一律不必兼容。**旧库拒开**属于这一档。
- 已定 · **四层**：格 / 载体 / hub / 索引库；`gc.py` 与这四层走**同一条路**（hub / pack / slot），
  只是换一套判据，不新开机制。
- 已定 · **索引只做索引**（2026-09-30 作者裁定）：库里每一个值都必须能从载体算回来。
  判据：索引里出现一个推不回来的值，它就不再是索引，而成了第二个事实源。
- 已定 · **查询是一条标准路**：拿 ID 查索引行 → 按行里的位置读载体记录 → 载荷里的引用又是 ID，
  再回索引。**顺扫是唯一例外**（输入载体、输出身份与位置），它不是第二条读路径。
- 已定 · **库的结构只有一条来路：ID**（2026-10-02 落定）：一个类型用了 ID，库里就有一张身份表；
  不用 ID，那张表自然不产生。`Block` 只是契约——锚定是"用没用 ID"，不是"是不是 Block"。
  判据：库里的行是 **ID 的镜像**，"某个字段进不去库"这个问题在代码上不成立。
- 已定 · **不再有表结构声明文件**：`config/tables.yaml` 与 `type.yml` 已取消、文件已删。
  表由"类型用了 ID"诞生；声明文件即便写出，系统也不读它——那是"文件与代码各说一套"的来源。

### 二、ID：身份，也是位置

- 已定 · **ID 是身份证，不是裸字符串**：含两套凭证（`value_uuid` 分配形态、`value_hash` 摘要形态）
  与身份字段。两套凭证**各有其用、并存不取**：**比较用分配形态，去重用摘要形态**。
  只留一套就会各坏一头——只留摘要则两次落盘同一内容无法区分与引用；只留分配形态则去重无从谈起。
- 已定 · **两种口径的字段清单不同，且这个不同是刻意的**：
  载体记录头带两套凭证 ＋ 名字 ＋ 签发时刻（**位置段不带**，"已经在那个文件里了"）；
  索引库的身份表列则**照搬 `ID_FIELDS` 七个字段**（含位置段三列），
  它要回答的恰是"这条记录在哪"，省掉位置就只剩全库顺扫一条路。
- 已定 · **位置段是投影**：写入后回填、删除时清空，盘上没有任何一份字节依赖它。
  故**不拿 `id.in_hub` 一类派生字段当持久事实**——压实、搬移之后它就会变，
  而派生值已经冻进载荷里了。
- 已定 · **摘要的写入口只有一条**：`ID.bind`。重复绑同一份内容是重放、放过；
  换内容即一份身份指了两份内容，当场报错。唯一例外是 `rebind=True`，**只给引擎用**——
  同一个块改了字段再存一次，块身份随载荷而变，那一项本来就该换。

### 三、记录与表

- 已定 · **块面 = 两条记录**：**内容记录**（载荷即内容，身份按内容签发，故同内容只存一份）
  ＋ **块记录**（载荷是指针加属性，身份是块自己的）；两条记录**各自提交，不是一次事务**。
  判据落在**载荷格式**上（保留键带 `\x00` 前缀），故类型为空也能列举、也能认出哪条是块。
- 已定 · **块记录的身份摘要恒为该记录自身载荷的摘要**：记录层的自校验就这么要求，
  故它**无法同时承载内容的摘要**。指向内容的凭证落在**块记录的载荷**里
  （保留键 `\x00cairn.ref`，`{value_uuid, value_hash}` 两套都带——只带摘要时
  "指向哪一条内容记录"只写得出一半）。指针在载荷里**不影响可重建**：顺扫读出载荷即得指针。
- 已定 · **类型标号不再单独落盘**：表名只由类名算出（`type(self).__name__.lower()`），
  **没有 `__table__`**，也没有第二个口子。**有多少个"用 ID 的类型"，就有多少张表**——
  名字是表的坐标，不是行里的判别列。
- 已定 · **身份表里不再有 `size` / `created` / `updated` 这类列**：大小在记录头里，
  而"落盘时刻"与 `birth_time` 是同一件事的两种写法——同一事实不写两处。
- 已定 · **`hub` 表退回"只有名字"**：它的真源是载体目录，登记只是投影。
- 已定 · **关系不落表**（2026-09-30）：关系由块自己表达，库只做索引；
  那张预先准备的 `edge` 表**已删**（零调用方，形状又按"关系是一等 DB 行"设计）。
  等真有领域产生关系时按那时的需要设计，**不预埋**。
- 未定 · **删掉类型要不要删表**：当前**只增不减**；删表属破坏性动作，须显式授权。

### 四、值决定落点

- 已定 · **落点写在类体上的声明里，不由代码分类**：`Attr("")` 进块记录载荷并**进反表**、
  `Body([])` 进内容记录、裸赋值照样落盘但**没有索引加持**。
  `Attr` 是描述符而非类型判据：实例里存的是裸值，声明活得比任何一次赋值更久。
- 已定 · **"声明了却不索引"是个假问题**：不要索引就别声明，裸赋值本来就落盘。
  故 `Attr` **没有 `indexed=` 这一类开关**——用了它就是要索引，没有中间态可调。
- 已定 · **声明必须放类体、不放 `__init__`**：放进构造里，这个实例字段的静态类型会变成声明类型，
  此后 `note.title = "标题"` 与它不符。类体是**字段类型与落点声明同时成立**的地方。
- 已定 · **类体上的默认值是共享的，故实例第一次取值时现拷一份**（容器现拷、标量原样）。
  这一步不能省：直接交还类体上那个列表，`first.lines.append(...)` 会改到所有实例。
- 已定 · **索引类型各自继承 `Block`，彼此平级**：`AttrIndex` / `BodyIndex` 直接继承基座，
  于是"用了 ID 就有表"这条在索引上照样成立，查索引时也知道它搁哪儿。
  **共用逻辑放模块级函数，不放中间基类**——那会多出一层"只为放代码而存在"的继承。
  **索引类型的发现靠 `manages` 声明，不靠继承**：按继承找会一个都找不到，
  而整条索引链会**静默失效**（表不建、行不写，只是查不到）。`owners()` 为此用了一次运行期导入，
  这是刻意付的代价。

### 五、正表与反表

- 已定 · **正表存在索引块的载荷里，反表在读时由正表现算，不存**。
  判据：存下来的反表要在写路径上增量维护，漏一处**不报错、只是查不到**；
  由正表翻过来的反表每次都是同一个答案。
- 已定 · **一条正表行一条记录**：写路径只有追加、没有改动，故不会出"改漏一处"的事故。
  同一个块同一字段写过多次，**最后写的那一条说了算**（块身份随载荷，改了字段就换了值）。
- 已定 · **索引块的体积上限取配置面的 `index.max.byte`**；块自己要用别的数才在类体上声明
  `max_bytes`——那里声明的是"这个类型要比默认更宽还是更窄"，默认值本身在声明处。
- 已定 · **索引值文本化时带类型名**（`int:1` / `bool:True`）：Python 里 `1 == True` 且哈希相同，
  不带类型名就会串。

### 六、载体与 hub

- 已定 · **两数格模型**：记录从格边界开始写，位置就是**头格与末格**两个整数，字节偏移由算术得出。
  作者的理由是"**存储怕的是存得莫名其妙**"——两数模型没有解释成本；
  三数模型带来的"槽对齐值 vs 实际占用"两套口径本身就是最难解释的那部分。
  代价被显式接受：一条记录至少占一格、格尾补零。
- 已定 · **载体自描述**：格长写进文件头，读取一律从文件头读，故改配置不会让已落盘载体的偏移错位。
  格号自文件头之后起算，故文件头不必凑成整格。
- 已定 · **封口是策略，不是状态**：文件里不留任何封印标记，"已封口"就是"达到了封口线"。
  判据取"**剩下的地方装不下下一格**"而非"长度达到封口线"——否则那一格白扔，
  而写入纪律本该是"写到满才换"。**单条记录大于封口线时照样完整写入**，否则大记录永远写不进去。
- 已定 · **活跃载体 = 有空间的最满者**：该判据不依赖时间戳与名字顺序，封口线调大后仍只有唯一答案。
- 已定 · **载体名取随机串**（无语义、无顺序号）：序号名在压实之后会被重用，
  而重用的名字会让**过期的索引行指向另一个文件**；随机名只会指向不存在的文件，**坏得看得见**。
- 已定 · **hub 是无状态的一层**：目录即存在证明（判据＝带 `packs/` 的直接子目录），
  格长随载体走、封口线每次写入按当前值判，故 hub **不存自己那份配置**；
  **读路径缺目录即报错，不悄悄建空 hub 顶上**。
- 已定 · **多 hub 的价值是确定性路径查询**：物理多 hub、引擎视角一块盘，查询两跳都是查表。
  故 hub 上取人话名或取 ID 形态没有区别；hub 本身**不持有 ID**（ID 是身份的，hub 是容器）。

### 七、删除与回收

- 已定 · **删除 = 追加墓碑 ＋ 摘索引行**，**墓碑必须落盘**：位置本来就是投影，
  只清内存里的位置等于没删。墓碑认的是**载荷摘要**而不是分配形态——块身份随载荷，
  同一份载荷只会有一份块记录，记摘要即够。
- 已定 · **判死活取"同一身份最后写的那条，再判它自己是否被墓碑标记"**：
  若改成"往回找第一条没被标记的"，删掉一次之后旧副本就会**复活**，而且不报错。
- 已定 · **字节由 `gc.py` 的 `sweep()` 回收**，四条判据一条都不能少——块记录取最后一条且未被标记、
  内容记录被活着的块指着、索引条目指着的块还活着、墓碑不保留。
  **一趟只扫一遍**并把全库记录连同位置收成一份抄本：分散去扫会出现"两处判得不一样"，
  而这种不一致不报错，只是多删或少删几条。
- 已定 · **挑载体由 GC 自己办**：它写**新的一份**，不参与 `hub.active` 的挑选——
  交给 hub 去挑会挑中还没清干净的旧载体，把新记录又写回待删的文件里。
  **没有死记录的载体原地不动**，否则每一趟都要把整库抄一遍。
- 已定 · **崩在半路不坏库**：新字节全部落盘之后才删旧载体，故最坏的情形是"两份并存、白占一份空间"，
  而两份内容逐字相同——记录自带身份，读哪一份都是同一个答案。
- 已定 · **删除有终局**：被删记录不再被报成缺失，也不会被任何补做动作补回来。

### 八、装配、配置与事件

- 已定 · **内核装配只做接线**：路径约定（`catalog.db` / `<hub>/packs/`）、`bind(engine)`、
  总线的失败钩子接日志。**一个进程一根线**，`close()` 解开。
  理由是引擎（哪个库根、哪个 hub）是**运行时**的事实，而类定义在 import 时就发生了。
- 已定 · **索引库是惰性开的**：`Kernel.create()` 只建目录，第一次真正要用它时才建文件——
  只读载体与巡检的场合不该凭空多一个库文件。
- 已定 · **存储那一层的配置声明在 `core/storage/conf.py` 一处、四条键**：
  `slot.max.byte.{b,kb,mb,gb,tb}`（五档**相加**为格长，全不写即报 `SlotSizeError`）、
  `pack.max.byte`（封口线）、`hub.default`、`index.max.byte`；内核自身那条在
  `core/conf/params.py`。**格长是格式事实**（写进文件头），另三条是策略（每次读当前值）。
  相加而非给一个"带小数的兆"，是为了不把浮点误差带进偏移算术。
- 已定 · **封口线必须一路传到载体**：`Hub.new_pack()` 漏传封口线时 `sealed` 会拿默认值判，
  而配置里的那个数**看起来生效、实际没有**。此类"配置看着生效、判定走默认值"的漏接是本层要防的一类错。
- 已定 · **事件只有两条**：`object.put`（落盘后发，`data` 带表名与内容地点）与 `object.deleted`。
  写路径经 `Engine(bus=...)` 发；不接线时照旧成立——**通知不是写成功的前提**。

### 九、未落地与已知缺口

- 未来项 · **重建与巡检的显式入口**：读路径已能在库缺失时回退顺扫，
  但"清空重扫、把库补齐"这个动作**尚未落地**；库内没有真源，故当前也不需要备份。
- 未来项 · **回收的调度**：`sweep` 存在，但**没有触发点**——命令面里没有它，内核也不自动跑。
- 未定 · **删除要不要判引用**：删除本身不判引用，`BodyIndex` 的引用数已可用，接线待定。
- 未来项 · **合并与短命 hub**（作者：短期不做）：并发承接 ＋ 合并回主 hub ＋ 销毁；
  同 ID 冲突按 `birth_time` 裁决。
- 现状限制 · **两条记录不是一次事务**：中途失败会留下孤儿内容记录——无害（无块指向它），
  但占空间，等下一趟 GC。
- 现状限制 · **跨设备字段不存在**：ID 上没有 `issuer` / `in_net_ip` 一类字段；
  跨端要补"在哪台机器上"，与关系设计一起定。
- 已定 · **能用块表达的一律用块**（作者 2026-09-30 定）：数据库没有那个"第三方视角"，
  它不站到旁边去表达"谁和谁有什么关系"，那是块自己的事。
