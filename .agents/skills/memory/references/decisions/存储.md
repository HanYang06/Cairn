## 存储（2026-10-02 裁定；同日落码）

> 状态：本文记的是 **2026-10-02 裁定**后的关键判断与理由，**已落码**（`eea635d`）。
> 设计细则以 `docs/architecture/py_core/storage/block-parts.md` 为准（载体字节布局见
> `docs/architecture/py_core/storage/pack-format.md`）；本文不复述细则，只留「为什么这么定」
> 与「为什么否掉别的做法」，以及 §十那几条只从代码里看得出的实现事实。

### 一、总口径

- 已定 · **从零重设计，不背兼容包袱**：无发布、无真实用户库（`git tag` 空、`version = 0.0.1`），
  故旧落盘格式、旧目录、旧 ID 一律不必兼容。**格式或库结构变更即拒开旧库与老载体**，
  不写兼容代码；迁移只随版本更新提供，非版本更新期间自行改动造成的损坏由使用者负责。
- 已定 · **四层**：格 / 载体 / hub / 索引库；回收与这四层走**同一条路**（hub / 载体 / 槽），
  只是换一套判据，不新开机制。
- 已定 · **索引库是权威视角**：它装**身份**（`name` / `value_uuid` / `birth_time`）、**位置**与
  **正文历史**，是这三样的唯一来源；载体装值，是值的唯一来源，**载体上不写一个字节的身份**。
  二者缺一，块都取不回来。
- 已定 · **权威视角只能落在库里**：位置与正文历史没有任何载体字节能算回来；要让它们可重算，
  就得把身份写进载体，而载体一旦写身份，搬移、改一段正文、回收都要改字节，槽的复用也无从判起。
  载体只装值，槽就是纯内容。
- 已定 · **查询是一条标准路**：拿 ID 查索引行 → 按行里的位置段读载体的槽 → 值里的引用又是 ID，
  再回索引库。**不设顺扫回退**：库里没有那一行即拒答，不按身份扫载体。
- 已定 · **库的结构只有一条来路：ID**（2026-10-02 落定）：一个类型用了 ID，库里就有一张表；
  不用 ID，那张表自然不产生。`Block` 只是契约——锚定是「用没用 ID」，不是「是不是 Block」。
- 已定 · **不再有表结构声明文件**：`config/tables.yaml` 与 `type.yml` 已取消、文件已删。
  表由「类型用了 ID」诞生；声明文件即便写出，系统也不读它——那是「文件与代码各说一套」的来源。

### 二、ID：身份三项，位置在库里

- 已定 · **身份字段收敛为三项**：`name` / `value_uuid` / `birth_time`。**`value_hash` 退出**，
  `ID.of` / `bind` / `bound` / `same_content` / `EMPTY_HASH` 一并退役。
  摘要那套凭证原本只为「同一份内容只存一份」而立，而这条如今由**正文索引块**承担
  （去重只针对 `Body`），ID 自己再带一列摘要就是同一事实写两处，两处必然分叉。
- 已定 · **位置段是段列表，且是位置的真源**：`in_pack_slot` 写在索引库，覆盖该块占用的
  **全部槽**（属性槽与正文槽）；规范形为升序、不重叠、相邻合并、段数最少，**改一次写一次**。
  它不是能从载体推算的派生值——派生值在搬移与压实之后就会变，而冻进字节里的那份不会。

### 三、记录与表

- 已定 · **块由属性槽与正文槽两个域组成**：属性槽装全部属性，**可原地覆盖**，不进历史；
  正文槽装正文分片，**只追加**，有历史。载体上不再有「记录」这一层，格的边界由文件头的格长定出。
- 已定 · **库的列不再等于 `ID` 的字段**：身份三项之外，库里另有**位置段**与**正文历史**两列，
  而 `ID` 上没有它们。判据：库是权威视角，它答的是「这个块是谁、在哪、正文经过哪些世代」，
  这三样在载体上都读不到。
- 已定 · **类型标号不再单独落盘**：表名只由类名算出（`type(self).__name__.lower()`），
  **没有 `__table__`**，也没有第二个口子。**有多少个「用 ID 的类型」，就有多少张表**——
  名字是表的坐标，不是行里的判别列。
- 已定 · **表里不存 `size` / `created` / `updated`**：大小由槽头的内容长度与位置段算回，
  「落盘时刻」与 `birth_time` 是同一件事的两种写法——同一事实不写两处。
- 已定 · **`hub` 表只有名字**：它的真源是载体目录，登记不承担定位。
- 已定 · **关系不落表**（2026-09-30）：关系由块自己表达，库只做索引；
  那张预先准备的 `edge` 表**已删**（零调用方，形状又按「关系是一等 DB 行」设计）。
  等真有领域产生关系时按那时的需要设计，**不预埋**。
- 未定 · **删掉类型要不要删表**：当前**只增不减**；删表属破坏性动作，须显式授权。

### 四、值决定落点

- 已定 · **落点写在类体上的声明里，不由代码分类**：`Attr("")` 落**属性槽**并进属性索引块、
  `Body([])` 落**正文槽**、裸赋值照样落盘但**没有索引加持**。
  `Attr` 是描述符而非类型判据：实例里存的是裸值，声明活得比任何一次赋值更久。
- 已定 · **「声明了却不索引」是个假问题**：不要索引就别声明，裸赋值本来就落盘。
  故 `Attr` **没有 `indexed=` 这一类开关**——用了它就是要索引，没有中间态可调。
- 已定 · **声明必须放类体、不放 `__init__`**：放进构造里，这个实例字段的静态类型会变成声明类型，
  此后 `note.title = "标题"` 与它不符。类体是**字段类型与落点声明同时成立**的地方。
- 已定 · **类体上的默认值是共享的，故实例第一次取值时现拷一份**（容器现拷、标量原样）。
  这一步不能省：直接交还类体上那个列表，`first.lines.append(...)` 会改到所有实例。
- 已定 · **索引类型各自继承 `Block`，彼此平级**：`AttrIndex` / `BodyIndex` 直接继承基座，
  于是「用了 ID 就有表」这条在索引上照样成立，查索引时也知道它搁哪儿。
  **共用逻辑放模块级函数，不放中间基类**——那会多出一层「只为放代码而存在」的继承。
  **索引类型的发现靠 `manages` 声明，不靠继承**：按继承找会一个都找不到，
  而整条索引链会**静默失效**（表不建、行不写，只是查不到）。`owners()` 为此用了一次运行期导入，
  这是刻意付的代价。

### 五、正表与反表

- 已定 · **正表随索引块落在载体的槽上，反表在读时由正表现算，不存**。
  判据：存下来的反表要在写路径上增量维护，漏一处**不报错、只是查不到**；
  由正表算出的反表每次都是同一个答案。
- 已定 · **正表按条追加**：写路径只有追加、没有原地改写，故不会出「改漏一处」的事故；
  同一个块同一字段写过多次，**最后写的那一条说了算**。
- 已定 · **索引块的体积上限取配置面的 `index.max.byte`**；块自己要用别的数才在类体上声明
  `max_bytes`——那里声明的是「这个类型要比默认更宽还是更窄」，默认值本身在声明处。
- 已定 · **索引值文本化时带类型名**（`int:1` / `bool:True`）：Python 里 `1 == True` 且哈希相同，
  不带类型名就会串。

### 六、载体与 hub

- 已定 · **定长格与算术定位仍然成立，位置是段列表**：格从文件头之后起算，每格长度相同，
  地址 = 24 ＋ 格号 × 格长，故格号到地址是常数时间、不查表；一个块占哪些槽由库里那一行的
  段列表给出，**不再是「头格与末格」一对数**。段列表的规范形（升序、不重叠、相邻合并、
  段数最少）让「哪些格属于这一块」只有一种写法；零散段合法，由回收收敛。
- 已定 · **格长只留两档**：`slot.max.byte.b` 与 `slot.max.byte.kb` **相加**得出；兆、吉、太三档清掉。
  多出来的档位只是把同一个数写成好几种拼法，而格长要写进文件头、成为格式事实。
- 已定 · **载体自描述**：格长写进文件头，读取一律从文件头读，故改配置不会让已落盘载体的偏移错位。
  格号自文件头之后起算，故文件头不必凑成整格。
- 已定 · **封口是策略，不是状态**：文件里不留任何封印标记，「已封口」就是「达到了封口线」。
  判据取「**剩下的地方装不下下一格**」而非「长度达到封口线」——否则那一格白扔，
  而写入纪律本该是「写到满才换」。**单条内容大于封口线时照样完整写入**，否则大内容永远写不进去。
- 已定 · **活跃载体 = 有空间的最满者**：该判据不依赖时间戳与名字顺序，封口线调大后仍只有唯一答案。
- 已定 · **载体名取随机串**（无语义、无顺序号）：序号名在压实之后会被重用，
  而重用的名字会让**过期的索引行指向另一个文件**；随机名只会指向不存在的文件，**坏得看得见**。
- 已定 · **hub 是无状态的一层**：目录即存在证明（判据＝带 `packs/` 的直接子目录），
  格长随载体走、封口线每次写入按当前值判，故 hub **不存自己那份配置**；
  **读路径缺目录即报错，不悄悄建空 hub 顶上**。
- 已定 · **多 hub 的价值是确定性路径查询**：物理多 hub、引擎视角一块盘，查询两跳都是查表。
  故 hub 上取人话名或取 ID 形态没有区别；hub 本身**不持有 ID**（ID 是身份的，hub 是容器）。

### 七、删除与回收

- 已定 · **删除 = 摘掉索引库那一行**，载体上不追加任何标记：库里没有那一行即读不到，
  字节仍留在载体上，回收另算。载体上不做删除标记——删除是库里的事。
- 已定 · **回收的判据是引用**：一个槽当且仅当没有任何索引行与任何正表行指着它，才可复用或回收。
  违反这条前提即读到别的块的数据，而且不报错。
  **一趟只扫一遍**并把全库的引用收成一份抄本：分散去扫会出现「两处判得不一样」，
  而这种不一致不报错，只是多删或少删几条。
- 已定 · **回收有两个触发点**：手动回收与自动回收（达到 `gc.auto.byte` 即触发），
  由模块级 `sweep(engine)` 承担；**触发点尚未接线**（见 §九）。
- 已定 · **零散段由回收收敛**：位置段允许零散形（合法），把散落的槽并回整段由回收负责。
- 已定 · **挑载体由 GC 自己办**：它写**新的一份**，不参与 `hub.active` 的挑选——
  交给 hub 去挑会挑中还没清干净的旧载体，把新槽又写回待删的载体里。
  **没有待回收槽的载体原地不动**，否则每一趟都要把整库抄一遍。
- 已定 · **崩在半路不坏库**：新字节全部落盘、库里的位置段改写之后才删旧载体，
  故最坏的情形是「两份并存、白占一份空间」，而两份内容逐字相同；库是权威视角，
  它指哪一份都是同一个答案。

### 八、装配、配置与事件

- 已定 · **内核装配只做接线**：路径约定（`catalog.db` / `<hub>/packs/`）、`bind(engine)`、
  总线的失败钩子接日志。**一个进程一根线**，`close()` 解开。
  理由是引擎（哪个库根、哪个 hub）是**运行时**的事实，而类定义在 import 时就发生了。
- 已定 · **索引库是惰性开的**：`Kernel.create()` 只建目录，第一次真正要用它时才建文件——
  只读载体与巡检的场合不该凭空多一个库文件。
- 已定 · **存储那一层的配置声明在 `core/storage/conf.py` 一处、七条键**：
  `slot.max.byte.b` / `slot.max.byte.kb`（**两档相加**为格长，全不写即报 `SlotSizeError`）、
  `pack.max.byte`（封口线）、`hub.default`、`index.max.byte`、
  `body.history.depth`（正文保留世代数）、`gc.auto.byte`（自动回收的阈值，`0` 即不自动回收）；
  内核自身那条在 `core/conf/params.py`。**格长是格式事实**（写进文件头），其余六条是策略
  （每次读当前值）。相加而非给一个「带小数的兆」，是为了不把浮点误差带进偏移算术。
- 已定 · **封口线必须一路传到载体**：`Hub.new_pack()` 漏传封口线时 `sealed` 会拿默认值判，
  而配置里的那个数**看起来生效、实际没有**。此类「配置看着生效、判定走默认值」的漏接是本层要防的一类错。
- 已定 · **事件只有两条**：`object.put`（落盘后发，`data` 带表名与内容地点）与 `object.deleted`。
  写路径经 `Engine(bus=...)` 发；不接线时照旧成立——**通知不是写成功的前提**。

### 九、未落地与已知缺口

- 已定 · **回收的两个触发点**：手动回收与自动回收（达到 `gc.auto.byte` 即触发）。
  `sweep(engine)` 与判据 `reclaimable_bytes(engine)` 都已落码，但手动那一头**没有触发点**
  （命令面里没有它，内核也不自动跑），自动那一头**没有接线到后台**。
- 未定 · **删除要不要判引用**：删除本身不判引用，`BodyIndex` 的引用数已可用，接线待定。
- 未来项 · **合并与短命 hub**（作者：短期不做）：并发承接 ＋ 合并回主 hub ＋ 销毁；
  同 ID 冲突按 `birth_time` 裁决。
- 现状限制 · **跨设备字段不存在**：ID 上没有 `issuer` / `in_net_ip` 一类字段；
  跨端要补「在哪台机器上」，与关系设计一起定。
- 已定 · **能用块表达的一律用块**（作者 2026-09-30 定）：数据库没有那个「第三方视角」，
  它不站到旁边去表达「谁和谁有什么关系」，那是块自己的事。

### 十、落码之后的实现事实（与设计页措辞有出入，以代码为准）

- 已定 · **库的列 = `ID` 的字段 ＋ `attr_in_pack_slot` ＋ `body_history`**：
  `attr_in_pack_slot` 记「这一块的属性槽是哪几格」。正文去重会让本块引用**别的块**的正文槽，
  那个格号可能比本块的属性槽更小，位置段归成规范形之后「末尾几格」这个切法就不成立，
  故属性槽另占一列。**否掉了**「靠位置段末几格推属性槽」这条。
- 已定 · **写侧的位置段次序有语义**（正文槽一段在前、属性槽一段在后，`ID.place_groups`）：
  规范形的「升序、不重叠、相邻合并、段数最少」用于**回收收敛与诊断**，不是写侧的摆放规则。
  归位会在「正文槽复用了别的块的、格号更小」这种场合把两组翻过来，而**不报错**。
- 已定 · **跨 hub 的正文复用是「复制一份到目标 hub」**（不是引用原 hub 的槽）：
  使一个块的全部槽落在同一个 hub，位置段只有一处载体名；代价是同内容在两个 hub 各存一份。
- 已定 · **正文槽上「槽复用的前提」被放宽**：去重本身就是让两个块指着同一格正文槽，
  故「有几行指着它」不再是禁止复用的判据，而是它活着的理由。
- 已定 · **按值查会滤掉已删块的行**：`Engine.read_index_rows` 按「库里还有没有那一行」判，
  故 `count` 不把旧行算进去。
- 已定 · **回收照旧搬索引块的槽**：`gc._identity_tables` 把索引块那两张表也算在内，
  故索引块的槽是活口、跟着搬，索引行的坐标跟着改写；但**回收不收敛索引块的位置段**
  （`2,4` 这样的写法搬完还在）。索引查询面接线时按这条验一遍。
- 已定 · **`Block.holds` 没有调用点**：正表行的形状由 `Engine.lay_index_row` 写，
  哪些列进哪一类索引由索引块的 `manages` 与字段的落点声明定；类方法 `holds` 留在基座上，
  默认交空映射，当前没有读点。**待作者确认**：是删掉，还是留给领域层自定义。

- 2026-10-02 · **按「块的组成与落点」裁定重写全文**：索引库是权威视角（装身份、位置与正文历史）、
  载体不写身份；身份字段收敛为三项；位置段是段列表、覆盖全部槽；删除即摘掉库里那一行；

  | 否掉了什么：投影纪律与「把库整个删掉系统仍必须正确」；顺扫重建与冷启动；
  按身份读取的顺扫回退与读回核对；「身份表少一列必须有重建入口」（改为拒开 ＋ 随版本迁移）；
  帧与帧表、信息格与数据格之分、身份帧、版本组与世代号、提交格、数据格头 32 字节与归属三字段、
  记录头与记录自框定；墓碑；两数格模型（位置＝头格与末格）；`value_hash` 与
  `ID.of` / `bind` / `bound` / `same_content` / `EMPTY_HASH`；格长的兆 / 吉 / 太三档。
