## 存储（现行；2026-09-30 表形状落定）

> 状态：**现行**，已落地并接进内核。**设计篇 `docs/architecture/storage-design.md` 是 L0 的唯一事实来源**，
> 细则以它为准；本文只记**关键判断与理由**，不复述细则。

### 一、总口径

- 已定 · **从零重设计，不背兼容包袱**：无发布、无真实用户库（`git tag` 空、`version = 0.0.1`），
  故旧落盘格式、旧目录、旧 ID 一律不必兼容。**旧库拒开**属于这一档。
- 已定 · **四层**：块 / 载体 / 多 hub / 索引库；**索引库是 hub 的组件**，不是与 hub 并列的一层。
- 已定 · **顺序：文档 → 类型与异常 → 字段 → 作者审字段 → 业务逻辑**。
- 已定 · **索引只做索引**（2026-09-30 作者裁定）：库里每一个值都必须能从载体算回来，
  **重建 = 扫所有块与基于块的数据结构**（配置、关系等内容不归索引管）。故 `kind`、`name`、
  `birth_time` 随记录落盘，位置段仍不落盘——记录被扫到时它在哪儿已由扫的动作给出。
  判据：索引里出现一个推不回来的值，它就不再是索引，而成了第二个事实源。
  两处尚未收口，见 §六。
- 已定 · **查询是一条标准路**：拿 ID 查索引行 → 按行里的位置读载体记录 → 载荷里的引用又是 ID，
  再回索引。**巡检 / 重建是唯一例外**（输入载体、输出索引行），它不是第二条读路径。

### 二、ID 与指针

- 已定 · **ID 是身份证，不是裸字符串**：含两套凭证（`value_uuid` 分配形态、`value_hash` 摘要形态）
  与身份字段。两套凭证**各有其用、并存不取**：**比较用分配形态，去重用摘要形态**。
- 已定 · **ID 的字段一个不少地进索引库**（`ID_FIELDS` 现算，含位置段三列），
  而**载体记录头只带两套凭证**。两套口径的理由不同：记录头是**载体格式**，
  省位置是因为"已经在那个文件里了"；索引库要回答的恰是"这条记录在哪"，
  省掉位置就只剩全库顺扫一条路。作者口径：**"ID 里没有哪个字段是存不进去的"**。
- 已定 · **`ID` 是给 body 用的、块与 ID 绑死**：body 持有 ID；块记录携带的是指向该 ID 的凭证。
- 已定 · **ID 管自身、载荷管指针**（修正早先的"一格两用"）：块记录的身份凭证 `value_hash`
  **恒为该记录自身载荷的摘要**——记录层的自校验就这么要求（解码时当场核对），
  故它**无法同时承载 body 的摘要**。指向 body 的凭证落在**块记录的载荷**里，
  保留键 `\x00cairn.body_ref`、内容为 `{value_uuid, value_hash}` **两套都带**
  （只带摘要时，块表里"指向哪份 body"只写得出一半）。
  指针在载荷里**不影响可重建**：顺扫读出载荷即得指针。

### 三、记录与表

- 已定 · **块面 = 两条记录**：**内容记录**（载荷即编码后的 body，身份按内容签发，故同内容只存一份）
  ＋ **块记录**（载荷是指针，身份是块自己的）；读回两条一拼。
  判据落在**载荷格式**上（保留键带不可打印前缀），故档一重建补回的块行照样认得出是块，
  **类型为空也能列举**。
- 已定 · **块记录与内容记录是两种记录，故索引要两层定位**。
- 已定 · **类型无界但只是继承层级，不是嵌套**；**类型标号随记录落盘**（2026-09-30 改；
  保留键 `\x00cairn.kind`，索引里的 `kind` 列是它的投影），不认识的 ID 一律**降级读回**
  （扫描 / 重建 / 合并都靠它，一处抛错即断链）。
- 已定 · **有多少个"用 ID 绑字段的类型"，就有多少张表**：`Block` → `block`、`Body` → `body`、
  领域类 → 它自己那张表。**名字是表的坐标**，不是行里的判别列。
- 已定 · **表的形状由类型登记现算，不走"手工建表"**：类型在**定义时被基座接管**
  （`__init_subclass__` → `adopt`：包一层 `__init__`、排一次零参探针），形状由**那一次探针**
  现收，再写进 `config/tables.yaml`、**由那份文件建库**。
  作者的原话判据：**"手工拆的与它自动拆的有明显区别"**——代码写好了，表自然拆得出来。
  **不取"运行期扫描全书"那条路**：慢，且会把没被导入的类型悄悄漏掉。
- 已定 · **有 ID 才有表**（2026-10-01 作者裁定）：`__init__` 里写了 `self.id = ID()` 的类型
  才登记、才建表；没写的是**只活在载荷里的结构**（值对象），不进登记表。
  即"由 block 把自己用 ID 的角色报给引擎，引擎据此处理"。
  连带：**`body` 表不再由类型诞生**，与 `hub` 同路由 `install_core_types()` 静态登记；
  `block` 指向 `body` 的两列是内在事实，不再从注解推。
- 已定 · **子类不继承父类的表名**：`__table__` 只认本类自己写下的那一个，
  否则子类会顶掉父类那张表，"一个类型一张表"当场垮掉。
- 已定 · **声明文件是"代码 → 文件 → 库"的中段，不是源头**：文件由代码写出、又被代码读回；
  **人是可以改它的**。写文件的口径是**只追加不覆写**，要淘汰的旧表由代码**显式点名**，不靠猜。
- 已定 · **两张表的列**：两张身份表的列 = **`ID` 的全部字段**（列名与顺序照搬，
  含位置段三列；`in_pack_slot` 是一对格号，落库写成文本 `头格:末格`），
  `block` 另有**指向 body 的两列**与类型标号 `kind`，`body` 则到此为止（**无 `kind`**）。
  故"ID 里的某个字段进不了库"在代码上不成立：清单从 `ID` 现算，不是另抄一份子集。
- 已定 · **不设 `size` / `created` / `updated`**：大小在记录头里（总长），
  而"落盘时刻"与 `birth_time` 是同一件事的两种写法——同一事实不写两处。
  位置段也不再另立 `hub` / `pack` / `slot_*` 那一套列名：库与 ID 一套词，改名即分叉。
- 已定 · **内容表也存位置**——每条载体记录都要有一行（档一、巡检、将来的压实都以盘为真源）。
- 已定 · **`hub` 不由类型诞生**：它的主语是载体目录（**表里只有名字**），
  不是"用 ID 绑字段的类型"，故照旧由声明层写死。
- 已定 · **关系不落表**（2026-09-30）：关系由块自己表达，库只做索引；
  那张预先准备的 `edge` 表**已删**（它零调用方，形状又按"关系是一等 DB 行"设计）。
  等真有领域产生关系时，按那时的需要设计"块怎么把关系说出来"与索引形状，**不预埋**。
- 未定 · **删掉类型要不要删表**：当前**只增不减**；删表属破坏性动作，须显式授权。

### 四、载体与 hub 的行为

- 已定 · **落地盘面**：定长槽（槽长随载体、写在文件头）、记录自框定（总长在最前）、
  **不设封口目录**（顺扫即可重建；目录只是优化）。
- 已定 · **hub 是无状态的一层**：目录即存在证明（判据＝带 `packs/` 的直接子目录），
  索引库里的 hub 表只是**登记**；槽长随载体走（文件头自描述），封口线每次写入按配置判，
  故 hub **不存自己那份配置**；**读路径缺目录即报错，不悄悄建空 hub 顶上**。
- 已定 · **封口不留标记**：没有封印字节、也没有封口文件，"已封口"就是"该载体达到封口线"，
  故封口是**策略判断**而非落盘状态。**活跃载体 = 有空间的最满者**——写入纪律是"写到满才换"，
  故该判据不依赖时间戳与名字顺序，封口线调大后仍只有唯一答案。
  **单条记录大于封口线时照样完整写入**（否则大记录永远写不进去）。
- 已定 · **载体名取随机串**（无语义、无顺序号）：序号名在压实之后会被重用，
  而重用的名字会让**过期的索引行指向另一个文件**；随机名只会指向不存在的文件，**坏得看得见**。
- 已定 · **多 hub 的价值是确定性路径查询**：物理多 hub、引擎视角一块盘，
  查询就是"先查 hub、再按槽区间读块"——**两跳都是查表**。
  故 **hub 上名称或 ID 没有区别**：hub 名就是目录名，取人话（`main`）或取 ID 形态对查询无影响；
  hub 本身**不持有 ID**（ID 是 body 的身份证，hub 是容器）。

### 五、维护：重建、巡检、处置

- 已定 · **重建分两种口径**：**档一重建 = 只补缺行**（已有行不动）；清空重扫属显式授权的破坏性动作。
  **每一列都能顺扫回来**（2026-09-30 起）：身份字段、类型标号与位置都在记录里或由扫到的位置给出，
  故索引库是纯投影，丢了重扫即可。
- 已定 · **巡检只报告、处置只补不删**：`patrol()` 把索引与真源两头对齐，发现按"可否由重建修复"分类；
  `repair()` 只动可修复的那部分——**内容没了、hub 没了、载体坏了一律不碰**
  （删行等于把"丢了东西"抹掉）。
- 已定 · **坏点即停属于重建、不属于巡检**：重建拿半份结果不能当结果；巡检要接着看完。
- 已定 · **索引库的可重建是逐表性质**：内核态可扫载体重建；领域态含真源在库内的表，
  损坏即**永久损失**，故**备份是必需能力**。
- 已定 · **表声明进配置，源码内不得出现建表 SQL**；只允许加、**破坏性变更拒绝启动**；
  建表只在开库 / 挂载，**不在热路径**。

### 六、已知缺口与未来项

- 已定 · **删除有终局**：`drop` 先写墓碑、再摘索引行；巡检按墓碑放行那些位置，
  故被删记录不再被报成 `missing_row`、也不会由处置补回来（曾列为待裁，已由墓碑解掉）。
  **内容字节仍留在载体里**，回收属压实那条未来项。
- 未来项 · **合并与短命 hub**（作者：短期不做）：并发承接 + 合并回主 hub + 销毁；
  同 ID 冲突按 `birth_time` 裁决。"合并期 hub 归属改写"随之推后。
- 未来项 · **压实回收**：删内容要判引用（同内容可能还有别的块在用）。
- 未定 · **列举仍会读全库正文**：去掉它要先把"块记录判据落成索引里的一列"，
  属设计篇 §12 的字段问题，**待作者裁**。
- 已定 · **关系的表达归块，数据库只做索引**（作者 2026-09-30 定）。
  判据是数据库没有那个"第三方视角"：它不站到旁边去表达"谁和谁有什么关系"，那是块自己的事
  （**块自己说它有哪些关系**）；库这边只把块说的翻成可查的形状（反查、将来的闭包）。
  故"能用块表达的一律用块"，关系索引表**不是关系的家**，它的每一行都要能从块重算。
  现状：库里的表只有 `block` / `body` / `hub`（+ 自用的 `meta`），关系索引尚未设计。
  两处真正的成本记在这里，免得重新论证一遍：**传递闭包**（解法是物化闭包表或图结构，
  等真实规模）与**跨 IP 的端点**（本地已是 `ID + 位置段`，跨端要补"在哪台机器上"，
  与关系设计一起定）。

### 变更记录

> 一条一行的索引：**改了什么 → 为什么 → 否掉了什么 → 后果 → Git**。
> 详细过程不在这里（那是 `git show <hash>` 的事）；**与事实不符或已被更大变化取代的条目，删掉**。

- 2026-09-30 · **身份列改为照搬 `ID` 的全部字段**（位置段按原名进库；删掉 `size` / `created` /
  `updated` 与 `hub` / `pack` / `slot_first` / `slot_last` 那套改名列）。
  | 为什么：ID 的 7 个字段本身就是完整的地址与身份表述，没有任何一个"存不进去"；
  原来的库只搬了其中 4 个、另给位置改了名，再掺进 4 个 ID 里没有的列，库与 ID 成了两套口径。
  | 否掉了什么：早先"位置段属推导面、绑不成列"的判断——**前提是已经找到那条记录**，
  而索引库存在的意义正是省掉全库顺扫。
  | 后果：`config/tables.yaml` 形状更换，**旧库须走授权重建**（只追加的声明文件不会自己删列）；
  `kind` 只活索引库这条缺口被凸显出来，见下一条。
  | Git：本条目随该次改动一同提交。
- 2026-09-30 · **类型标号随记录落盘**（保留键 `\x00cairn.kind`），`name` / `birth_time` 一并进记录；
  索引里的 `kind` 列由 `prog` 改判为 `store`（顺扫可见）。
  | 为什么：作者裁定"库是索引、索引要确定性"——重建只需扫块，索引里不得有推不回来的值。
  原先 `kind` 只活索引行，索引一重扫全库的块就不知道自己是什么类型，"可重建的投影"当场不成立。
  | 否掉了什么：把类型标号写进载荷那条路——同一段 body 会被不同类型的块用（内容按地址去重），
  写进载荷就把去重切碎了；也否掉了"承认索引带真源、改档为 source"那条路。
  | 后果：记录头段变大（每条多约 40~60 字节，槽浪费已计入既有取舍）；载体布局版本不变
  （ID 段是 CBOR 映射，未知键本就忽略），旧记录仍读得回；`block` / `body` 的"档一可重建"
  至此成立。
  | Git：本条目随该次改动一同提交。
- 2026-09-30 · **`hub` 表退回"只有名字"**（删 `role` / `state` / `created`）；
  `repair()` 与 `rebuild()` 的 `now=` 参数随之取消。
  | 为什么：作者裁定"库=索引、重建只需扫块"——那三列从 hub 目录推不出来，
  留在表里就等于索引揣着真值。短命 hub 与合并将来落地时，真源放 hub 目录（标记文件）再投影。
  | 否掉了什么：把"第一次见到这个 hub 的时刻"当登记信息留着。
  | 后果：`rows.register_hub(name)` 只剩一个参数；`config/tables.yaml` 的 hub 表一列。
  | Git：本条目随该次改动一同提交。
- 2026-09-30 · **删掉 `edge`（关系索引）表**：表声明、行层三个方法、两个单测一并删。
  | 为什么：它**零调用方**（全仓只有测试在调），形状又按已被否掉的"关系是一等 DB 行"设计
  （带 `domain`、身份是 `(src,dst,kind,domain)` 的摘要）；留着就是脚手架，且是错形状的脚手架。
  | 否掉了什么：把它当"将来的索引"预埋；也否掉了同一天早些时候给它定的 `source` 档
  （档对了，形状不对，所以整张表都不留）。
  | 后果：内核表只剩 `block` / `body` / `hub`（+ 自用 `meta`），与作者的心智模型一致；
  关系落地时按那时的需要重设索引形状。文档里"关系是 DB 行"的旧口径一并改掉。
  | Git：本条目随该次改动一同提交。
- 2026-10-01 · **"摘块与巡检的相互作用"由"待裁"改判为"已定"**（删除有终局）。
  | 为什么：墓碑已落地——`drop` 先写墓碑再摘行，巡检按墓碑放行，被删记录不再被报成
  `missing_row`，处置也就不会把它补回来；旧条目描述的故障在代码上已不成立。
  | 否掉了什么：把它继续挂在"待裁"里（记忆与代码不符即失真）。
  | 后果：内容字节仍留在载体里，回收仍属压实那条未来项。
  | Git：见本次提交（墓碑本体为 `60bba19`）。
- 2026-10-01 · **§三"手工拆表"那条改写**：登记由"定义时完成"改为"定义时接管、
  零参探针首次被问到时现算"；并新增"有 ID 才有表"（`body` 表改与 `hub` 同路静态登记）。
  | 为什么：块形状改为在 `__init__` 里声明（作者裁定，见 [`内核.md`](内核.md) §七），

  | 后果：登记表多一份待探清单；值对象不再登记（它们没有 ID）；`tables.yaml` 与库的形状不变。
  | Git：见本次提交。
