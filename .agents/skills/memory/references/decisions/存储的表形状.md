## 存储的表形状（2026-09-30 作者裁定：**一名一表 + 表会自己诞生**，已落地）

> **已落地**（2026-09-30 片 11）：`record` 单表与 `id(scope).name` 判别列已退役；
> 两张身份表 `block` / `body` 由 `Body` / `Block` 两个类型定义时登记而诞生。
> 实现见 `src/core/storage/{registry,tablegen}.py`；链路口径见设计篇 §8.2.1。

- 已定 · **有多少个"用 ID 绑字段的类型"，就有多少张表**：`Block` → `block`、`Body` → `body`、
  领域类 → 它自己那张表。**名字是表的坐标**（`id(block).…` 指向 `block` 表），
  不是行里的判别列，故身份表主键就是 `value_uuid`。
- 已定 · **表的形状由类型登记现算，不走"手工建表"**（作者 2026-09-30 追述）：
  运行顺序是 ① 解释器跑起来、类型定义；② **ID 侧有反查机制**——谁用了它就登记；
  ③ 由登记现算表名与列，写进 `config/tables.yaml`，**再由那份文件建库**。
  作者的原话判据：**"手工拆的与它自动拆的有明显区别"**——代码写好了，表自然拆得出来。
- 已定 · **反查的落点是 `__init_subclass__`，不是运行期扫描全书**（我按代码定的实现）：
  `Body` / `Block` 在定义时登记自己；`@dataclass(slots=True)` 会重建类、故同形状重放视为幂等。
  扫全仓模块是另一条路，慢且会把没被导入的类型漏掉，不取。
- 已定 · **子类不继承父类的表名**：`__table__` 只认本类自己写下的那一个，否则子类会顶掉
  父类那张表，"一个类型一张表"当场垮掉。没写就按类名推。
- 已定 · **声明文件是"代码 → 文件 → 库"的中段，不是源头**：文件由代码写出来、
  又被代码读回去；故**人是可以改它的**（加了列下一轮只补不删），不被跳过。
  写文件的口径是**只追加不覆写**：登记表里没有的旧表要淘汰，由 `Kernel` 显式点名
  （`SUPERSEDED_TABLES = ("record",)`），不靠猜。
- 已定 · **块载荷里的指针带两套凭证**（2026-09-30 作者确认）：`{value_uuid, value_hash}`，
  保留键 `\x00cairn.body_ref`。只带摘要时块表里"指向哪份 body"只写得出一半。
- 已定 · **两张表的列**（按现有声明口径推，已落地）：
  `block` ＝ 自己的身份 ＋ 指向 body 的两列 ＋ `kind` ＋ 位置观测列 ＋ 两个时刻；
  `body` ＝ 身份 ＋ 位置观测列（**无 `kind`**：内容记录不带类型标号）。
  **内容表也存位置观测列**：每条载体记录都要有一行（档一、巡检、将来的压实都以盘为真源）。
  代价如实记：同一位置在两张表各有一份，两份都是同一批字节的投影。
- 已定 · **`hub` / `edge` 不由类型诞生**：`hub` 的主语是载体目录、`edge` 的主语是关系本身，
  两者都不是"用 ID 绑字段的类型"，故照旧由声明层写死（`tablegen.KERNEL_EXTRA_TABLES`）。
- 已定 · **旧库拒开**：`record` 表不再合声明，属"不背兼容包袱"（设计篇 §9.6）那一档。
- 未定 · **删掉类型要不要删表**：当前只增不减；删表属破坏性动作，须显式授权（设计篇 §12）。
