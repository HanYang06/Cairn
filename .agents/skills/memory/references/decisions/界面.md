## 界面 / UI（现行；2026-09-30 Qt 退场后重定）

> 状态：**现行**。本文只记**现在成立的约束与理由**。
> 历史（为什么当初选 Qt、又为什么退）不在这里堆——那是 Git 的事；
> 被否掉的**路径**要留，因为它是唯一的防复发依据。

### 一、材质与技术栈（2026-09-30 定）

- 已定 · **界面材质 = Tauri 壳 + Web 前端（React / TypeScript + Vite）**；Python 内核以
  **边车（子进程）**运行。Qt（PySide6 / Widgets / QML / QSS）整条退场。
- 已定 · **壳用 Tauri 而不用 Electron**：不随包塞一份浏览器内核，体量差一个量级。
- 已定 · **Rust 正式进入技术栈**：Tauri 的壳本身就是 Rust。
  旧的"Rust 仅在性能热点被证实后启用"**作废**——那条管的是"把 Python 热点下沉到 Rust"，
  与壳无关。想用就用，不因为文档里两句话否掉决定。
- 已定 · **工具链**（2026-09-30）：`pnpm`（严格依赖隔离，与"声明之外的就不该能用"一致）+ `Biome`
  （lint 与格式合一，一个工具一份配置）+ **TypeScript**（与本仓 `mypy strict` 同口径）+
  `Vite` + `Vitest`。**框架 React 属作者偏好**，不是推导出来的唯一解。
- 已定 · **仓库布局**：`src-tauri/`（Rust 壳）/ `frontend/`（React）/ `src/core/`（Python 内核）/
  `src/app/`（Python 侧入口）。原 `src/app/<平台>/` 的平台分目录**随 Qt 作废**——
  壳是跨平台的同一份 Tauri 工程。
- 已定 · **`ui_tools` 这个层名随 Qt 作废**：它原本指"不认识领域、也不碰 `core.storage` 的 Qt 工具箱"；
  该职责由 `frontend/` 的共享组件与原子承担，**边界判据不变**。

### 二、通信：两个边界，第②跳已定（2026-09-30）

```
React(TS)  ──①──  Rust 壳(Tauri)  ──②──  Python 内核(边车)
   WebView 进程          壳进程              Python 进程
```

- 已定 · **第①跳不自研**：WebView ↔ Rust 由 Tauri 自带（`invoke()` 与事件系统），
  参数与返回值**都是 JSON 序列化**——这正是"契约必须生成"的根因，不是可绕开的选择。
- 已定 · **第②跳 = stdio + 长度头分帧 JSON**（与 LSP 同款，壳把边车当子进程起）。
- 已定 · **本地内核不开任何网络端口**。理由（作者口径）：**网络这一层要留给 server 与 P2P 那条线**，
  两条线若都走网络就共用同一个面，运维与排查互相干扰。原话："单独给它开个网络确实不太合适……
  后面有 server、P2P 这些东西，那边又要网络，如果两边都是网络的话，运维有点费劲儿。"
- 已定 · **推送方向单独设计**：前端 → 内核是"调用"，内核 → 前端是"通知"（带订阅标识）；
  **壳只转发，不做决策**。
- **已否掉的路径**（勿重开）：本地 HTTP / WebSocket——省分帧，但要处理端口分配与占用、
  监听面能被别的进程连上、防火墙弹窗、边车变孤儿进程；**留作后手**，真要"多客户端"或
  大规模流式再谈。**PyO3 把 Python 嵌进壳**——少一层序列化，但打包要把 CPython 嵌进壳、
  Python 依赖变成壳的构建产物，升级与运维复杂度反而最大。
- 已定 · **三条随通信形态生效的硬约定**：① Rust 壳里**不许出现领域字段名**（命令面只是一个转发口，
  壳一旦解构领域字段，业务就漏进壳）；② **大载荷传句柄不传内容**（`value_uuid` 这类不可解读的
  引用，由内核按句柄取）；③ **二进制走原始字节通道**，不必全域 base64。

### 三、契约与令牌（两处**未定**，动手前必须先定）

- 未定 · **契约的类型同步**：领域契约（fields / actions / signals）必须同时是 Python 与 TS 的类型。
  两处边界会把类型洗两遍（Python 出门即无类型 JSON，再过 IPC 到 TS 只剩手写 `interface`），
  而"两份事实"正是本项目要防的架构偏移。**倾向"单一事实源 + 生成"**（仓内先例：
  `tools/docgen.py` 从声明现算 + 防漂移用例）；需先定事实源放 **Python** 还是 **中立 schema**。
- 未定 · **外观令牌的落地机制**：CSS 自定义属性，或由声明生成令牌模块。
- 已按作者口径记下的方向（尚未落成机制）：**尽可能少写 CSS**——"写多了只会导致一个结果，
  就是样式绑定不统一"；做法是把样式绑进组件、上层只做编排，**边距 / 圆角 / 阴影一律不写**。

### 四、性能口径（设计时就认下来）

- 已定 · **冷启动**：第一次调用要等 Python 解释器起来与开库（数百毫秒到数秒），
  故边车要么先起、要么把"库打开"做成一次握手，界面配启动画面。
- 已定 · **往返次数**：前端逐字段发调用等于"渲染一次、几十次 IPC"，
  故内核短面要**按用途批量**（列表一次取一页），不按字段取。
- 已定 · **底层的八件事**：分帧、请求—响应配对（id）、错误跨进程、
  通知通道（订阅 id）、二进制通道、就绪与版本握手、边车生命周期、超时与取消。
  **前四件必须一次做对**（它们是协议本身）；后四件在第一片壳落地时只做最简版。

### 五、UI 内核（架构主张，与材质无关）

`docs/architecture/ui-kernel.md` 是设计总纲。要点（**与 Qt 时代口径相同，全部继续有效**）：

- 已定 · **UI 内核 ≠ 任何具体材质**：它负责「对象 → 界面」的生成 / 编译 / 绑定 / 配置。
- 已定 · **单向数据流**：内核 → 投影 → 视图；视图 → 意图 → 命令 → 内核。
  **不引入响应式框架 / reconciler / 双向绑定**。
- 已定 · **数据直通 = 信号代理 + 投影 + 命令**：两端各设代理，**代理即稳定面**；
  绑定对象因此必然存在。变更流向：内核 → 数据侧代理 → 投影缓存 → UI 侧代理 → 界面。
- 已定 · **界面只消费中立类型 + 领域契约 + 投影**；**不 import `feature`、不导入 `core.storage`**；
  界面里出现 `bucket` / `block` / `body` / `attrs` / `checksum` / `type=notedata` 即失控。
  判据（验收问句）：**若理解某个界面组件需要先掌握存储实现，则边界已失效。**
- 已定 · **契约属领域、渲染归 UI**：领域只声明"具备什么"（fields / actions / signals），
  界面决定"呈现为何"；领域**不指定控件、不接触界面框架、不涉及像素**。
- 已定 · **契约不得长在 `Block` 上**：字段描述符（`Attr` / `Data`）属存储机制，
  在内核边界内投影为中立 `FieldSpec`，界面只读它。
- 已定 · **快捷创建 = 对象驱动生成**：由领域对象分析出界面初稿 + 套通用架构默认行为，
  开发者只改细节。**特化优于通用**；自动生成**只出初稿**，细节不猜、不假装已实现。
  验收指标：加领域字段 = 领域一处（+ 显示提示），界面 **0~1 处**；加标准动作 = 契约一处。
  **若加一个字段仍需改 5 个界面文件，则设计失败，应回头修订契约。**
- 已定 · **字段显示提示固定四词**：`label` / `group` / `display` / `editable`；
  **能按类型推的不写**。取值由领域给，界面照做。
- 已定 · **领域无需额外手写契约清单**：它在对象自身已有的声明就是契约
  （字段注解 / 动作声明 / 信号声明）。要求每个领域先写一份 fields/actions/signals 清单是**过度**。
- 已定 · **组件的 `__init__` 写什么就是什么**：分析是**浅的、确定性的**（不做运行时推断、
  不做代码生成器级分析）。同一条也约束"生成"：只做确定性动作。

### 六、事件层（口径，不是实现）

- 已定 · **事件只做扇出通知、不做决策**；**不建解析器 / 中介者**。
  理由即判据：**有没有调用方**——当前内核没有任何命令路径与结果回执需求，
  先建中介者就是无调用方的框架，违背"未实现的设计标为预留"。
  （`core/event/parser.py` 的空桩已删。）
- 已定 · **重启条件**：出现真正的命令路径（上层要"做这件事，把结果给我"）或网络侧上线
  （事件变成数据流，需要"解码包 → 决策 → 执行"）时再设计，届时按**类型化处理器 + 中介者**重做。
- 行业依据（记下免得再论证一遍）：Guava 官方文档开局劝退 `EventBus`、
  Django 官方文档劝"能直调就别发信号"——两支主流都认为事件该少用、只做通知。

### 七、构建规则（与材质无关）

- 已定 · **联动在控制器，不在控件之间**：组合式组件用共享控制器 / 状态对象协调零件；
  零件只发意图，**禁止控件间直接互连**（否则成蛛网、无法复用）。
- 已定 · **布局靠原语嵌套组合**：底层只 `VBox / HBox / Grid / Split / Stack` 一类，
  复杂结构由嵌套 + 权重拼出，**不新增原语**。
- 已定 · **组合可递归**：组合类型可再组合、深度不设限；再组合出来的类型仍归"组合"本身，
  **只增复杂度，不增概念**。
- 已定 · **增长只在原子与页面**：加控件只改原子目录，加功能只改页面组合，内核与外壳保持稳定。
- 已定 · **主题 = 点分配置 → 编译**：配置只覆盖能集中管理的观感（色 / 圆角 / 间距 / 字号 / 字体 /
  动效）；阴影 / 动效等由组件按令牌值实现，**逐条加、可测、有边界**。
  组件内**禁止硬编码颜色 / 间距 / 圆角**。

### 八、组装与生命周期

- 已定 · **App = 组合根 / 编排层**：组合内核 + 领域 + 界面，并按平台发布。
  界面外壳在 App 层，**领域界面也在 App 侧**（不进工具箱）。
- 已定 · **跨域协作由 App 承担编排**，不靠"共享层"。
- 已定 · **App 拥有生命周期与启动**：开库 → 组装 → 套主题 → 建窗 → 事件循环；
  启动样板不暴露给使用者。
- 已定 · **根布局三带**：顶带（工具栏，相对固定）+ 舞台（主区）+ 任务栏（长期任务）；
  边缘（导航 / 检查器 / 关系 / 版本）按需出现、默认收起；专注时全隐。
- 已定 · **捕捉与整理 = 同一空间换态**（不另开捕捉窗）：浏览（卡片流）/ 专注（一卡占满）/
  组织（看板 / 画板）。
- 已定 · **笔记与项目同构**：舞台只有「卡片」一种单元；项目 / 组 / 标签是**镜头（过滤器）**，
  不是顶级分区。"进项目" = 换镜头，不是换世界。
- 已定 · **卡片四粒度**：卡 → 展开（卡内编辑）→ 专注（占满）→ 落板（拿空间坐标）；
  规则视图是派生、画板是手动覆盖。
- 已定 · **两种密度**（只留两种）：卡片（大 / 中图标）/ 详细（列表）；混排靠 `kind` 颜色区分。
- 已定 · **顶带 = 工具栏**：搜索 / 命令常驻，其余功能走**伸缩抽屉**。
- 已定 · **工具底座 = 大方框 + 格子 + 槽（无任何业务词汇）**：根是空的大方框，
  作者自由搭出任意结构；槽用 `expects=` 声明等谁的哪个部件。
  **工具里不留 `topbar` / `navigator` / `content` 这类预置区域。**
- 已定 · **谁定义标签，标签归谁**：App 的槽名 App 起，Part 的部件名领域起，**不代定义**。
- 已定 · **槽只管自己的行为**（弹性 / 滚动 / 对齐 / 隐藏 / 锁定 / 容量），**不管内容怎么显示**。
- 已定 · **组件 / 布局只被页面或 Part 消费**；App 不直接吃组件与布局。
- 已定 · **外观唯一真源 = 主题文件**（`config/theme/*.json` 一类），由点分配置编译；
  组件只引用令牌。壳**不得绕开工具箱用裸框架搭**。

> 它们描述的是**产品与结构口径**，材质换成前端后由 `docs/architecture/ui-theme.md`
> 与 `rules/references/ui-boundary.md` 承担落地表述。
