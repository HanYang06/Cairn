## 内核重建（2026-09-29 定）

- 已定 · **旧实现整条作废，推倒重建**（作者口径）：分支 `refactor/clean-local-code` 删除 `src/` 全部旧实现、
  `tests/` 全部测试与 `docs/review/ocr-2026-09-22.md`，相对 `main` 共 137 个文件 / 21045 行。
  判据：内核只该管事件 / 存储 / 配置 / 异常四件事，总量应当很小；旧实现已偏离该目标。
- 已定 · **新代码方向是事实源，文档随后回写**（作者裁定）：`kernel-spec.md` / `kernel.md` /
  `storage-design.md` / `AGENTS.md` 里的旧口径暂不作为实现依据，冲突处以新代码为准。
- 已定 · **代码优先、注释写在现场**：落代码时把设计意图直接写进 docstring；文档、记忆与仓库尾巴
  （`tools/`、CI、`mkdocs.yml`、`pyproject.toml` 中指向已删模块的引用）统一后补。
- 已定 · **随片带最小回归测试**：每落一片内核配对应契约测试，不再攒到最后统一补。
- 已定 · **ID 凭证算法取 `uuid4` + `sha256`**（2026-09-29）：不使用 26 字符 Crockford ULID 与 BLAKE3；
  理由是不需要时间排序（ID 已带 `birth_time`，排序需求本身不强），且实现更短。
  切换点是 `format/id.py` 的 `new_uuid()` 与 `digest()` 两个函数。
- 已定 · **事件分发自制，不引第三方分发库**（2026-09-29，实测后定）：先选 blinker（MIT / 零依赖 /
  Pallets 维护），实测三条与本内核需求冲突——① 投递顺序取 `set` 迭代序（注册 a、b、c，实测调用序
  a、c、b），跨次运行都可能不同；② 订阅者抛错中断后续订阅者；③ `weak=True` 默认静默丢弃闭包与
  局部函数。覆盖这三条后轮子只剩字典记账（约 30 行），故改为自写 `core/event/bus.py`（约 70 行、零依赖），
  契约钉死为：按注册顺序投递、异常隔离并把失败清单交回调用方、显式撤订（句柄或上下文管理器）、失败钩子。
  blinker 装上后已 `uv remove` 撤净。另一路（引 blinker + `ordered-set` 换顺序）被否：是在运行时改
  第三方库的类属性，且依赖从一变成二。
- 已定 · **事件对象字段借 CloudEvents 口径**（2026-09-29）：`id` / `source` / `type` / `time` /
  `subject` / `data`；**只借名，不代表实现该规范**（无 `specversion`、无传输绑定），
  `cloudevents` SDK 不引（自称 work in progress，且多两个依赖）。
- 已定 · **载体记录头的 ID 段只带两套凭证**（2026-09-29）：§5.3 的散文与 §3.5 的持久化子集表冲突
  （前者说含名字 / 签发信息 / 桶 / 载体，后者明确这些不写、只留两套凭证）；判据取 §3.5——
  必需子集才落盘，名字由容器给出、位置由目录与载体推出、时间属程序信息。`from_record` 对可选字段
  宽容读回、未知键忽略，故将来要加字段不必改旧记录的读法。**不伪造签发时间**：记录里没有即取 0。
- 已定 · **hub 是"桶"的新名字**（2026-09-29，作者裁定）：`in_hub` = 在哪个 hub、`in_hub_pack` = hub 里的
  哪个载体；`vault`（库根）由打开时的上下文给出，不占 ID 字段。故 `storage/bucket.py` 改名
  `storage/hub.py`（判据不变：`vault/` 下带 `packs/` 的直接子目录才算 hub），代码与注释一律用 hub；
  `storage-design.md` 词汇表与 §6/§7 的"桶 / bucket"待回写时统一改词。
- 已定 · **槽位定位取两数格模型**（2026-09-29，作者裁定，推翻设计篇 §5.2 的紧凑模型）：
  载体是一串等大的格子，**记录从格边界开始写，写不下就往后再拼格子**；一条记录的位置就是
  **头一格与末格**两个数字（`SlotRange(first, last)` 闭区间）。作者的理由是"存储怕的是存得莫名其妙"——
  两数模型没有解释成本；三数模型（紧凑排布 ＋ 槽内偏移）带来的"槽对齐值 vs 实际占用"两套口径，
  本身就是最难解释的那部分，故一并删除（`aligned_slots` / `occupied_slots` / `head` 全部不存在）。
  **代价被显式接受并钉进测试**：一条记录至少占一格，格尾补零，故**槽长必须从设计篇的 64 KiB 降下来**
  （本项目取 512 B 作推荐：平均浪费 256 B/条，2 GiB 载体约 420 万格）。`storage-design.md` §5.2/§5.6
  待回写时按此改正。
- 已定 · **载体文件头 24 字节 = 魔数 8 ＋槽长 8 ＋预留 8**（2026-09-29）：魔数 `CAIRNPK1` 末位带布局
  版本；槽长写进文件头、读取一律从文件头读（§5.5），故改配置不会让已落盘载体的偏移错位；
  预留段不校验内容，留给将来加字段。**格号自文件头之后起算**，故文件头不必凑成整格。
- 已定 · **事件层只做扇出通知，不建解析器／中介者**（2026-09-29，作者交办代定）：判据是"有没有调用方"——
  当前内核没有任何命令路径与结果回执需求，先建中介者就是无调用方的框架，违背「未实现的设计标为预留」。
  `core/event/parser.py` 的 `EventParser` 空桩已删除（全仓无引用）。**重启条件**：出现真正的命令路径
  （上层要"做这件事，把结果给我"）或网络侧上线（事件变成数据流，需要"解码包 → 决策 → 执行"）时再设计，
  届时按形式二（类型化处理器 + 中介者）重做。行业依据：Guava 官方文档开局劝退 `EventBus`、
  Django 官方文档劝"能直调就别发信号"——两支主流都认为事件该少用、只做通知。
