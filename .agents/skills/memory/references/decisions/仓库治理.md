## 仓库治理（现行）

> 状态：**现行**。本文只记**现在生效的约束与理由**；过程见文末的变更记录。
> **AI 与人工的形态差异已取消**（原「隔离开发环境」整节删除）：不做双状态、不分授权。

### 一、提交与合并

- 已定 · **`main` 只接受 PR**：远端 ruleset「Protect main」（匹配 `~DEFAULT_BRANCH`）在
  `deletion` / `non_fast_forward` / `code_quality` 之上，加入 `pull_request` 与
  `required_status_checks`（必需检查仅 `quality`，`strict_required_status_checks_policy=false`）；
  `bypass_actors` 为空，规则对 admin 同样生效。
  | 理由：**约束目标 ref，而非约束动作**。本地合并是纯客户端行为、服务端不可见，任何本地钩子
  都可被 `--no-verify` 或改写 `core.hooksPath` 绕过；且 `pre-merge-commit` 对快进合并不触发
  （分支自 `main` 拉出、`main` 期间未动时合回即快进，不产生合并提交）。
  改为约束 ref 后，快进 / 合并提交 / rebase / cherry-pick / 网页与 API 直改一律归约为
  「更新 `refs/heads/main`」，全部拒绝；合法写入只剩服务端 PR 合并。
- 已定 · **不设「禁止本地合并」规则**：该约束在 Git 中无法成立，
  且会误伤「把 `main` 合入特性分支」这一正当操作。规则只针对合入 `main` 的方向。
- 已定 · **`build` 与 `deploy` 不作必需检查**：`docs.yml` 与 `build-windows.yml` 的 job 同名 `build`
  且带 `paths` 过滤，未触及相应路径的 PR 永远等不到该检查，会使 PR 长挂等待；
  `deploy` 仅在 `main` 上运行。
- 已定 · **提交授权不按分支区分**：在非 `main` 分支上正常 `commit` / `push` 即可；
  **合入 `main` 必须先经作者同意**（并由服务端规则强制）。细则见 `rules/references/commit.md`。
- 已定 · **本地钩子必须先安装，且它不随 clone 走**：`.pre-commit-config.yaml` 只是配置，
  `uv run pre-commit install --hook-type pre-commit --hook-type commit-msg` 才把它写进
  `.git/hooks/`。2026-09-30 实测：配了 5 个钩子而**一个都没跑过**（`.git/hooks/` 里只有
  Git LFS 装的 4 个）——「文件里有配置」不等于「门禁生效」。
  故**判断生效与否看 `.git/hooks/`，不看配置文件**；新环境第一件事就是装钩子。
  （钩子仍只是"提前反馈"：它可被 `--no-verify` 绕过，真闸门是 CI 与 `main` 的 PR 规则。）
- 未定 · **`required_approving_review_count` 现为 0**：GitHub 不允许自批，
  待首个 PR 由作者人工批准后再升至 1。**升至 1 之前，不得声称存在人工评审闸门。**

### 二、代码与门禁的落位

- 已定 · **`tools/` 与 `scripts/` 按"能不能被 import"一刀切**（2026-09-30 作者定）：
  `tools/` 是正规包（有 `__init__.py`），装**可被 import 调用**的可调用件——
  mypy 插件（`pyproject` 按路径引它）、原子写与输出助手 `_iosafe`；
  `scripts/` 的门禁与生成器（SPDX / 书面语 / 标点 / 提交信息 / docgen / 打包）。
  | 理由：作者口径——**工具是可被调用的，脚本是不可被 import 的**；
  两者混在一处时，"这个文件能不能 import"要靠读代码才知道。
  | 做法：`scripts/` **不放 `__init__.py`**，声明"这不是一个包"；
  但**光靠这一点拦不住**——Python 3 的命名空间包（PEP 420）照样 `import scripts.xxx`（已实测），
  故真正的拦截是 **import-linter 契约**：`core` / `tools` 不许依赖 `scripts`（违反即 BROKEN，已实测）。
  | 后果：`mypy` 的文件清单变成 `py_src tools scripts tests`；门禁命令一律写 `scripts/…`；
  `[tool.importlinter]` 用 `root_packages = ["core", "tools"]`（`lint-imports` 是控制台脚本，
  仓根不在 `sys.path`，只列 `core` 时一写 `tools` 就报"模块不存在"）。
  | Git：`git log --grep="scripts"`。

### 三、身份与凭证

- 已定 · **不得改动 git 配置与凭证**（`user.*`、`core.sshCommand`、远端 URL、`gh` 登录态）。
- 已定 · 提交身份用 `<id>+<login>@users.noreply.github.com` 形式，保证归属可查。

### 四、可见性与工作树

- 已定 · **可见性靠 Git，不靠共享目录**：成果以已推送为准，**未推送视为未完成**。
  用户侧以 `git fetch` + `git diff HEAD...origin/<分支>` 或 PR 评审查看。

### 变更记录

- 2026-09-30 · **`tools/` 与 `scripts/` 分开**（判据：能不能被 import）＋ **本地钩子改为已安装**。
  | 为什么：作者口径"工具可被调用、脚本不可被 import"；且当天实测发现
  `.pre-commit-config.yaml` 配着的钩子**一个都没跑过**（`.git/hooks/` 里只有 Git LFS 的四个）。
  | 否掉了什么：把门禁继续留在 `tools/`（"能不能 import"靠读代码才知道）；
  以及"配置文件在就等于门禁生效"这个假设。
  | 后果：`scripts/` 不放 `__init__.py` 只作意图声明，**拦截靠 import-linter 契约**
  （`core` / `tools` 不许依赖 `scripts`）；mypy 清单加 `scripts`；新增门禁一律落 `scripts/`。
  钩子须逐机安装，且可被 `--no-verify` 绕过——真闸门仍是 CI 与 PR 规则。
  | Git：`git log --grep="scripts"`。
- 2026-09-30 · **取消 AI 与人工的双状态**（作者裁定）：原「隔离开发环境」整节删除。
  删除的约束：AI 分支统一 `ai/` 前缀、独占工作树（WSL 发行版 `cairn-ai`：关闭 automount、
  `interop` 不追加 Windows 路径、`ai` 用户不入 `sudo` 组、仓库克隆置 Linux 文件系统）、
  「按分支分授权」（`ai/*` 自行提交推送、其他分支只读）、「隔离成立的前提是 agent 进程运行在
  `cairn-ai` 内」。
  | 理由：给 AI 与人工维护两套状态本身就是常驻负担（作者口径：麻烦，不搞）。
  | 后果：AI 与人工共用同一工作树，故**同一时刻只应有一个写者**；成果仍以推送为准。
  | 另：`main` 只经 PR 的规则**保留**——它是保护而非隔离，放开它等于允许直推 `main`。
  | 是否连 `main` 保护一并取消，**待作者明示**，不要代为删除远端规则。
  | Git：`git log --grep="取消 AI 与人工的双状态"`（本条与它所改的文件同一个提交，
  故不写死短哈希——哈希写进自己那个提交里会随 amend 失效）。
