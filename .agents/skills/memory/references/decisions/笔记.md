## 笔记（2026-10-01 作者口述布局；实现未开始）

> 状态：**方向已定、代码未落**。本文记笔记对象的内容模型（资产 / 画板 / 正文 / 工具型结构）。
> 领域层的继承、登记与职责见 [`领域.md`](领域.md)；L0 的块与载体见 `docs/architecture/storage-design.md`。
> **读法**：`docs/architecture/note-model.md` 与 `domains.md` 都是**草案**，其中若干条已被新口径取代。
> **冲突时以本文与代码为准**，旧稿只提供背景，不作依据。

### 一、资产（多模态）

- 已定 · **媒体归一个通用"资产"块**（作者 2026-10-01 定）：继承 `Block`，**媒体种类是类型字段的事**，
  不是三个并列类型。故"加一种媒体"= 加一个类型值，不动表结构。
  （**名字取 `Asset`**：`docs/architecture/access.md` 讲的是**可见性档位**，与资产是两件事，
  两词不得混用。旧口径"三个字段＝图片 / 视频 / 音频"**已被本节取代**。）
- 已定 · **媒体种类由 `mime` 与元数据决定，不由类型名决定**：渲染策略确实分几档
  （可解码图像 / 时序媒体 / 文档），但那是**由 mime 现算的策略分类**，不落成三个类型——
  三个枚举装不下 gif / webp / svg / pdf / 字幕 / 波形 / 附件。
- 已定 · **对已压缩格式，"无损压下去"没有空间**：JPEG / PNG / WebP / AV1 / H.264 / Opus
  都已做过熵编码，无损再压通常只有个位数百分比。**真正能压的只有"重复"与"冗余副本"**，
  故体积这件事的战场是**去重**，不是压缩。
- 已定 · **读取速度的杠杆不是"文件变小"，而是三件事**：本地缓存命中、**按段取**
  （HTTP `Range` / 分片）、**给列表用小素材**（缩略图 / 首帧 / 波形），
  不为显示列表去解码整份媒体。故"引用媒体要有加载"本质是**加载分三层**
  （先小素材 → 再按段取原件 → 同时缓存预取），限流下的体验靠"先小后大 + 缓存"缓解。
- 已定 · **本地优先的底线是离线可用**：OSS（对象存储）只能是**副本 / 旁路**，
  本地必须留缓存（按需 pin + LRU），否则断网即残。**未来项**：媒体外置到 OSS，
  服务"资源很多"的用法；它属网络那条线，不与内核面共用。
- 已定 · **音画同步由"两块是否配得上"判定，不靠名字相等**：名字会改、会重名，不足以作判据；
  判据取**可核对的客观量**（时长、时间基 / 采样率、起始时间戳）。校验**属领域自建**——
  内核没有跨字段校验钩子（见 [`领域.md`](领域.md) §三）。
- 已定 · **逐帧图片化不作存储形态**（作者已自行判断"体积变大"，成立）：视频靠**帧间冗余**
  压体积，逐帧存图等于放弃它，通常大一个数量级以上。**抽关键帧**（封面 / 缩略图 / 检索）
  是常规做法；**发布**要的那个好处来自**分片**（HLS / DASH 的 segment + 关键帧对齐），
  不是逐帧图片——项目里"大正文分片"正是这条预留（`storage-design.md` §6.3）。
- 已定 · **资产块装"引用"**（已随"一切皆引用"裁定，见 §三）：行里只留类型 + ID 串，本体各自成块。
- 已定 · **媒体打包粒度**（作者 2026-10-01 定）：**一份媒体一个容器、整份塞二进制**，
  不重新编码（"拆又拆不开"，转不转通用码都行）；**取的时候做字节分片**（纯字节分片，简单）。
  **不必上内容定义分块（CDC）**：CDC 的价值在"内容会移位"的场景（可编辑文档、目录镜像），
  而媒体是整体替换的，固定分片足够。
- 已定 · **媒体分片做在存储时**（作者 2026-10-01 定，取 b）：存时就切片、一片片读，
  以支持"只读一部分"（大视频、网络传输、内存受限）。
- 已定 · **分片由领域实现，内核不动**（作者口径：对底层的块而言，它不关心载荷是什么）：
  上层把一份媒体切成 **N 个普通块**（各自 `store`），另存**一个清单块**引用这 N 个片；
  顺序由清单里的列表表达，部分读就是按清单逐个 `load`。
  即设计篇 §6.3 的"part 块 + index 块"，只是**由领域搭**而不用内核内置——
  内核的 `PART_TYPE` / `INDEX_TYPE` 预留**代码里零痕迹**，不必等它。
  片的粒度取固定值即可（媒体整体替换，不需要内容定义分块）。
- 已定 · **格式能力不构成约束**：MP4 / MOV / MKV / WebM 本就是容器，
  **带声音的视频本身就是"视频＋音频一个容器"**。故打包粒度**按"引用粒度"定，不按"能不能装"定**。

### 二、画板

- 已定 · **不是嵌套，是 ID 引用**（作者口径）：组合与画板之间的从属由身份引用表达，
  与"跨块引用由块自己表达"一致。
  **单向引用很自然；反查（谁引用了我）要索引，"被引用者被删"要判引用**——两者均未设计。
- 已定 · **画板分两部分**：图画模型（可直接取用的图形数据）与**组合**；组合本身也是画板对象。
- 已定 · **图形 = 指令 + 参数**（作者口径：靠"一些动作"确定线条往哪走，把它"描述成一种路径"）。
  即**矢量显示列表 / 路径指令集**，标准形态是 SVG path 的 `M / L / C / Q / A / Z`；
  作者所记的"有这种算法"即**贝塞尔求值**与**路径扫描转换**（描边 / 填充）。
  **裸点坐标列表不足以确定图形**，必须带"怎么连"的指令。
- 已定 · **矢量与位图分两份载荷**：矢量（几何图形、箭头等非几何图形、部分 SVG）可无损缩放、
  可编辑、体积小；位图（纯点阵、手绘栅格）保真但不可编辑。两者**不许混在一个列表里**。
- 已定 · **画板内容分三层**：矢量图形层、位图层、**文字层**；文字层**直接复用 `NoteData`**。
- 已定 · **画板不做动画**（作者口径："动画体系真的烦死人了，我是要挑战 Flash 吗"）：
  画板只做静止图形，取路径指令。若将来真要做，**另立时间轴**（关键帧 / 缓动）——
  那是一套独立的东西，不塞进画板几何。
- 已定 · **图元类型是开放字符串 + 一份"图元库"**（作者 2026-10-01 定）：写作时写的是图元名，
  渲染时**先去库里找**，有就取出来、没有就报错（"没有这个图"）。故**加载顺序是先读库**
  （我有哪些图），用户用的都是库里已有的。库的落点**待定**（Python 里的一份登记 vs 一份数据文件）。
- 已定 · **一枚图不存"我连着谁"**：关系由连线表达（`CanvasLink.figures` 列出被连的图）。
  同一张板上再存一份就是同一条事实写两处。
- 已定 · **连线只记语义**（连哪些图 / 怎么连 / 标签 / 线型），**不存折点**：几何归自动布局，
  故手绘走向不会被原样复现，而是给一套自动优化的——优化就发生在绘制过程中，
  用户只管"拽图形、确认关系"。

### 三、正文

- 已定 · **正文存为 `NoteData`**，链接等附属信息**随文字一起表达**（不另设关系表）。
- 已定 · **外层是有序列表，以"行"为存储元素**（作者 2026-10-01 定）。
  **不得用以行 id 为键的映射**：行序不在行数据里，而规范 CBOR 的映射按键排序，
  项目的 ID 是 `uuid4`（`id.py`），排序结果与文档顺序无关——存下去再读回来整篇会打乱。
- 已定 · **行的颗粒度只认换行符**：一个换行符即一行，**不得拿标点或字符数当分行的依据**。
  与既有口径一致（硬回车是段落边界、软换行只是显示、**内核不强制拆行**）；
  超长行由界面处理（关软换行、转横向滚动），不在数据里切。
- 已定 · **`linetype` 是语义枚举，不装属性**：它只回答"这行是什么"
  （文本 / 链接 / 媒体 / 图画 / 标题 / 列表项 / 代码 …）；它同时是**判别位**，
  读 `data` 时按它分支，故不得是自由文本。细分参数（媒体 mime 与尺寸、标题级别一类）
  随该行自己的结构走，**不塞进枚举**。
- 已定 · **除正文文本外，一切内容皆引用**（作者 2026-10-01 定）：链接、媒体资产、图画画板
  都只在行里写**类型 + 一串 ID**，本体各自成块；拿到 ID 看类型，再去对应的表查。
  → §一"资产块装引用还是装内容"**就此裁定：装引用**。
- 已定 · **`data` 可以是任何东西**（字符串 / 一组对象 / ID 串），但须满足三条：
  ① **确定性可编码**——同一逻辑内容必须编出同一段字节，否则内容地址漂移、去重失效；
  ② **形态由 `linetype` 决定**（判别联合）；
  ③ **`linetype` 同时是引用解析的入口**——它的值域必须能与"引用目标住在哪张表"对上
  （内容类如文本 / 链接；块类如资产 / 画板 / 嵌入的笔记），这份映射要**一处定义**，
  否则"看类型去查"没有依据。
- 已定 · **行条目取单字段形式；样式按作用域分两种，`NoteStyle` 是笔记级那一份**：

  ```
  body     = [ NoteLine, … ]                          # 外层列表保序
  NoteLine = [ id, linetype, data, linestyle?, spans? ]
  spans    = [ (start, end, spanstyle), … ]           # 行内区间，有序
  ```

- 已定 · **`spans` 是有序列表，允许多个样式并存、后写覆盖前写**（作者口径）：
  不是"一个样式把整行定死"——先写的管一段，后写的可覆盖重叠处，未被覆盖的部分保留前者。
  故**"行样式"就是这份区间列表的统称**（"行样式与 `spans` 是不是一件事"就此裁为**一件事**）。
- 已定 · **落盘前归并**（作者 2026-10-01 裁定走甲）：编辑期允许多个样式分层、后写覆盖前写；
  **落盘前归并**成"不重叠、有序、去默认、相邻同样式合并"的规范形态。
  视觉结果不丢，丢的是操作顺序（那属撤销栈，不属盘上）。
  若不归并，同一视觉效果会有多份写法，而块身份按载荷摘要算——
  "看起来一样的两行"就会得到两个内容地址，去重失效。

- 已定 · **样式分两个作用域，不得混**（作者口径）：
  **(a) 笔记级 = `NoteStyle`**，塞在 `NoteData` 里，管**整篇**长什么样（背景一类），是全局样式；
  **(b) 行级样式**，塞在行里，管这一行与它的文字（作者原话：像插入一段 LaTeX）。
- 已定 · **样式写法取 KV**（作者裁定）：属性名 → 值。属性清单**参照 CSS 的文本子集**
  （粗体 / 斜体 / 下划线 / 删除线 / 颜色 / 背景 / 字号 / 字重 …）。
  **两道闸**：① **只收文本呈现、不收布局**（边距 / 圆角 / 阴影不进正文，项目口径是
  "页面里一个都不写"）；② **取命名的值、不取字面量**（颜色写主题令牌名，不写 `#rrggbb`），
  否则正文里会出现与主题脱钩的硬编码，前端"令牌唯一真源"当场分叉。
  **代价须认**：正文因此与令牌词表耦合，令牌改名要迁移正文。
  名词说明：所谓"短键映射"就是 KV、只是键名取短；"位标志"是把多个布尔压进一个整数
  （省字节、难读、难演进），**不取**。
- 已定 · **属性清单不靠人背**（作者口径："样式太多了，别让我背"）：**取一份现成子集起步、
  按需增补**——参照富文本编辑器通行的 mark 集（粗体 / 斜体 / 下划线 / 删除线 / 行内代码 /
  上标下标 / 文字色 / 背景色 / 字体族 / 字号 / 字重 …），落到代码里"逐条加、可测、有边界"。
  **不做一次性穷举，也不要求作者先行枚举。**
- 已定 · **键名与取值照抄行业，不自创**（作者 2026-10-01：现成的东西能抄就不要另定，
  还须顾及行业习惯）：**键用 CSS 的文本属性名**（`font-weight` / `font-style` /
  `text-decoration` / `color` / `background-color` / `font-size` / `font-family` …），
  **值用 CSS 的值**。于是颜色这类"命名值"不需要另发明语法——**CSS 的 `var(--color-…)`
  本身就是令牌引用**；这套 KV 到前端近乎直通，不另设翻译层。
  （此条取代此前"KV 键名与命名值形态"的待裁。）
- 已定 · **标题分两层，不是一处**（作者口径）：
  **文本级大标题**是 `NoteData` 的属性——`title`，可再加 `subtitle`
  （与 `note-model.md` §2"标题是描述字段、不是正文的一部分"一致）；
  **文本内标题**是行级——`linetype = 标题`，级别随该行的行级参数走。
- 已定 · **文本内标题的级别缺省取最大**（作者口径）：不带级别就是最高一级
  （HTML 里最大是 `h1`，"H0" 不是标准名）。级别是**行级参数**；
  按"去默认"的规范化，缺省值**不写进载荷**。
- 已定 · **样式挂在行上**（不再另立"行 id → 区间"的第二张表）：读一行即得它的样式，
  行表与样式表不必互相同步，删一行不留孤儿样式。
- 已定 · **`NoteLine` 与 `NoteStyle` 是载荷内的值对象：不登记、不建表**
  （登记的是 `NoteData` / `Asset` / `Canvas` 这些块）。同族先例：`BodyRef` / `BlockPayload` /
  `Tombstone` / `SlotRange`。**"触手"原则的边界就在这里**：内核需要认出来的才登记；
  只在载荷内部、随载荷一起重建的结构不需要。
- 已定 · **元组与字典的取舍不按"少两个字段"算**：两者体积账相当（映射头约省 4 字节/行，
  而字典可以**不写空字段**，多数行没有段落属性）；**定论只有两条**——
  ① **顺序必须靠外层列表**；② **演进上字典赢**（字典是名字契约，未知键可忽略，
  项目已有此口径；元组是位置契约，加字段要同步改所有读点）。
  而**正文的演进特别贵**：编码一变内容地址全变、去重池整份作废，且"手工版本号"已被裁掉，
  没有版本标记可依赖。故取"**有序列表 + 每行一个 KV**"这条稳的。
  （尾部的可选元素可"短一个"省掉，故普通行不为样式付开销。）
- 已定 · **规范化是硬要求**（否则同一逻辑样式编出不同字节，内容地址漂移、去重失效）：
  区间**不重叠、按起点升序**；**去默认**（默认样式不写）；相邻同样式**合并**；空区间不写；
  无样式省略可选项；同一含义只有**一种写法**（如颜色统一写令牌名）。
- 已定 · **行内偏移必然随行内编辑漂移**（作者口径：影响不大，改动时重算一行即可）；
  **行级稳定性由行 id 保证**（增删与重排不影响其它行）。
- 已定 · **设计原则**：快捷编辑、存储方便、样式编辑便捷三者并重。
  行序即落盘形态；行内编辑的 rope / piece table 属**内存结构**那一侧，
  留出将来换的余地（触发条件按项目口径：热点被证实）。
- **废止** · `note-model.md` §2「没有链接语法：链接是独立的关系行」——那是与已删 `edge` 表
  同一批的旧口径，**作废**；现行口径是"关系由块自己表达，库只做索引"。

### 四、工具型数据结构

- 已定 · 除主体之外还有一组结构：**`NoteDiff`**（版本与比较）、
  **`NoteGroup`**（分组 / 集合）、**`NoteEdge`**（笔记之间的关系）。
- 已定 · **不再分"工具型"与"业务型"，所有实体块一律可查**（作者 2026-10-01 定）：
  不存在"这类块不进列举"的类别；查询面的代价由界面承担——**多开两个查询界面**即可，
  界面按 `kind` 分屏，内核只如实列举。`Nature` 那套声明随之全砍
  （见 [`内核.md`](内核.md) §六）。
- 已定 · **`Note edge` 表示笔记之间的关系**：派生（A 派生自 B、B 派生自 C）、
  发布后被他人改动一类。作者口径：**这种关系可以很明确地形成**。
- 已定 · **它是"块表达出来的关系"，不是库里的关系索引表**：存储上由块把关系写进自己的载荷，
  库只把块说的翻成可查的形状（2026-09-30 定）。**名字与已删的 `edge` 表不是一回事**
  （那是表名，且形状按"关系是一等 DB 行"设计）。
  **反查与传递闭包要索引**（物化闭包表或图结构），等真实规模，**不预埋**。
- 已定 · **结构化数据的落点由"要不要能查"决定**（三条，防它到处乱长）：
  ① **要能按它查、或有反查** → 落成**块属性**（`attr[...]` + `__indexed__`），跟块走；
  ② **只影响这一行怎么显示与编辑** → 随行走在行里（KV）；
  ③ **只是某个值内部的结构** → 值对象，留在载荷里。
  判据仍是项目那条：**能用块表达的一律用块**；库里的表要等"推不出来又必须跨块查"才配。
- 已定 · **清单（作者 2026-10-01 列）**：标题 / 副标题（§三）、**标签**、**时间**、
  **待办状态**、**列表层级**、**表格**、**自定义字段**。
- 已定 · **标签 = `NoteTag` 块，形态是"标签表"**（作者 2026-10-01 定）：载荷是 **KV**，
  **K 是标签、V 是笔记 ID 的列表**，故一个标签可被多篇笔记引用，**反查是读这一个块**。
  未来可在此之上升级出"领域标签"。
- **关键** · 这个形态把"列表"从**笔记的属性**挪进了**标签块的载荷**，于是
  **标签名成了标量属性**（可进速查）：按标签找笔记 = 按名字查到标签块 → 读它的成员列表，
  **不必全库顺扫**。此前记的"现算派生倒排"方案因此作废（它只是没有标签块时的退路）。
  代码依据：内核**明令禁止**容器类型进速查——`__indexed__` 点名 list / dict 会在**声明期**
  抛 `TableDeclarationError`，理由写着"容器值不可哈希，按它查只能是「包含」式，不值当——
  **要查就拆成标量属性**"（`core/storage/registry.py`）。
- 已定 · **只有一个真源：标签块；笔记里写的是"名字"不是 ID**（作者 2026-10-01 定，
  解掉双向权威问题）：笔记照旧用 `#` 井号字符串写标签；写完**发一个动作**到标签侧"我要添加"，
  **由标签侧裁定**——已存在就回"已存在"，不存在就加进去。**调用方不自查**
  （省一遍检查，且判定只有一处）。反向查询就用标签块。
  于是两边不再是两个真源，而是"**一边主动、一边被动**"，被动那侧不产生冲突。
  代价须认：**名字即引用 ⇒ 标签改名会让笔记里的名字悬空**。处理办法已定
  （作者 2026-10-01，**改口径：采用与视频平台一致的做法**）：
  **改名 = 一个新标签**；旧的那份成为**空悬标签**，由**回收机制**清掉（长期无人使用即回收）。
  **不做重定向、也不做别名**。作者的理由是语义上的：**改名的行为本身就是想把含义变掉**；
  若别人仍能用旧标签搜到这些内容，这次"含义变更"就没有真正发生——单人本地看不出差别，
  社区化时才会显现（大厂按此设计自有道理）。
  两条落地要说清：① **"长期没被利用"需要一个时间量**，而 `birth_time` 每次保存都会换，
  故领域必须**自己带**"最后使用时间"之类的字段；② **自动回收等于自动删用户数据**，
  而内核只有墓碑（给巡检看的，**不是回收站**）——要么回收前由用户确认，
  要么领域自留恢复窗口。
- 已定 · **`NoteGroup` 取乙**（作者 2026-10-01 定）：**一个组一个块，组里嵌组**——
  成员是笔记 ID，子组是别的组块的 ID。**不设递归深度上限**（作者口径：叠得深是用户自己的事）。
  **但实现上有一条**：遍历必须**迭代**而非递归——不设上限可以，
  但"用户叠得深"不该变成"程序爆栈"，那会变成程序自己的问题。
  再补一条（作者 2026-10-01）：到某个深度时**由界面给警告**（黄 / 红），
  说明已达该深度、依当前设备性能建议不再加深、建议拆分；**"一键拆分"暂不做**
  （真拆还是假拆都先不考虑），当前只做**纯警告**。
- 已定 · **标签与分组在结构上同构**（都是"名字 → 一串笔记 ID"的有序 KV），
  差别只在语义（标签平铺多对多、分组可嵌套有序）。**这是"抽共享件"的合格理由**——
  第二个调用方已经存在；但两者仍是**两种类型、两张表**（名字是表的坐标）。
- **已砍 · 变更记录整体推迟成预留**（作者 2026-10-01，判据是**零调用方**）：
  diff 那一摊整条删掉（`types/diff.py`、动作词表、相关用例），声明文件里 `notediff`
  那张表也点名淘汰。理由不是"它麻烦"，而是**零调用方即脚手架**——与 `edge` 表被删同一个判例；
  它顺带消掉了"什么算一次版本"这个一直没定的悬案。
  **素材没丢**：正文每次保存都是一份完整的、按内容地址去重的记录；将来要加版本，
  只需一个"把某份正文登记成版本"的动作。
  **重启条件**：出现真正的调用方（界面要看历史 / 要回滚）时再设计；届时先答三问——
  ① **什么算一次版本**（自动保存与检查点的边界）；② **一步记什么**（**只记动作不记内容**：
  记了内容它就成了正文的副本，既冗余、又不好分享）；③ **链放哪儿**（一个块 vs 一步一块，
  判据是槽位——一个块最少占一格）。
- 已定 · **笔记级样式是 `NoteData` 的属性**（`style`，纯字符串 KV），**不进正文**：
  正文按内容地址去重，写进去就等于"改一次背景把整篇重存一遍"。故 `NoteBody` 里**只有行**；
  那个曾经叫 `NoteStyle` 的值对象类型**已删**（键序交给规范 CBOR，去默认交给写路径）。
- **更正** · **"不设创建与更新"是存储层对 `block` 的限制，不是领域的限制**（作者 2026-10-01 纠正；
  此前把它套到领域是越界）。领域该加就加：笔记的创建时间与修改时间都正常作属性

  它随每次签发变（`store` 每次新签 ID），**每次保存都会得到新的 `birth_time`**。
- 已定 · **待办状态分两层**（作者口径）：整篇可有一个待办状态；
  行内部也可以有待办状态，**那本身就是一个行结构**（如 `linetype = 待办` + 状态）。
- 已定 · **自定义字段**：可做，但**必须讲明：不参与速查**（作者口径，与代码一致——

- 已定 · **列表层级与表格：先分清两种，再决定要不要结构**。
  **(a) 正文里的缩进列表**：不必另设结构——行级 KV 一个 `level` 就够（行级下硬做这二者确实费劲）；
  **(b) 作为对象被引用的列表 / 表格**：**各自成块**（`ListData` / `TableData` 继承 `Block`，
  继承即登记即建表），行里只留**类型 + 一串 ID**，与"一切皆引用"同一条路。
  判据仍是"能用块表达的一律用块"；表格单元格若又要富文本，注意递归深度。
- 已定 · **领域 API 面（作者 2026-10-01 列，未实现）**：样式（查样式 / 查全部样式 / 查已存在的样式）、
  行（查行 / 查全部行 / 查行类型 / 编辑行）、资产与其它（查资产、顺引用一路查、关系）。

  故领域侧要有"打开笔记"的**会话缓存**（正文解一次，行与样式查询在内存里答）；

### 五、当前真正的缺口

- **二进制通道尚未接线**：命令面这一版所有载荷走 base64（`core/api.py` 自述
  "大正文的原始字节通道尚未接线"），前端传一部片子既慢又占内存。
  按 `ui-boundary.md` §四"大载荷传句柄不传内容"，正解是前端持句柄、**字节由壳侧按句柄取**
  （原生资源协议 / 文件句柄）。
- **去重粒度只有整份载荷**：子文件级去重要靠**内容定义分块（CDC）+ 块级去重 + 哈希树**
  （行业入口：Spacedrive 白皮书、OxiCloud 的 FastCDC + BLAKE3 方案）。
  **仓内预留**：`fastcdc` 与 `blake3` 已声明在 `pyproject.toml` 却零引用（见 `progress.md` 依赖盘点）。
- **引用完整性未设计**：删除不判引用（压实才判），反查要索引。
- **块体积与配额**：`__max_block_mbyte__` 等声明与 `PACK_MAX_BYTES` / `SLOT_BYTES` 决定一份
  媒体落得下多大、要不要另开载体；单条记录大于封口线时照样完整写入。
- **大内容分片是预留**：`PART_TYPE` / `INDEX_TYPE` 与 `storage-design.md` §6.3 已定词表，块面未接。
