## 文档（2026-09-26 定 + 已落）

- 已定 · **文档分两条线，不许合并**：**手写事实源**（`docs/**/*.md` + `README.md` + `AGENTS.md` +
  `py_src/**` 的 docstring，跟代码一起评审）与 **自动生成**（配置参考页 + `docs/api/` 的 API 参考 + `site/`）。
  **API 说明一律不手写**——手写的那份必然过期、与代码不符。生成走 griffe AST 解析（不执行代码）。
- 已定 · **生成的第一判据：能算的就不写、能查的就不写**（2026-09-26 补，作者质疑"生成是零"后立）：
  只要内容**已存在于代码 / 配置声明 / schema**，就该**投影**而不是抄。据此已落两件——
  ① **配置参考页** `docs/reference/config.md` **整页由 `scripts/docgen.py` 生成**
  （取自配置声明现算的词表投影；含 SPDX 头与「勿手改」声明，正文零手写），
  **入库** + `--check` 防漂移；② **docstring 覆盖报告**（AST 统计，暴露"没写 docstring 的公共成员
  会从 API 页静默消失"这个此前不可见的事实）。
  **"生成"不包括 API 参考里那些 docstring**——那是人写在代码里的，工具只做搬运。
- 已定 · **生成物入库 vs 不入库，看它是不是给人读的**：`site/`（整站）不入库；
  给人读的**生成页入库**（`docs/reference/config.md`），好在 GitHub 上直接读、也能用 `--check` 比对。
- 已定 · **能用生成文件解决就别上 MkDocs 钩子**：钩子放在 `docs/` 下会被静默忽略
  （`docs/` 被当包目录，与导入撞名）；生成文件 + 防漂移门禁更好验证。
- 已定 · **工具链 = MkDocs + Material + mkdocstrings**（不用 Sphinx）：Material 中文支持好、
  Markdown 即源码（现有 `docs/` 零迁移）、API 抽取与 docstring 风格（google）天然对齐；
  **许可干净**：`mkdocs-material` MIT、`mkdocstrings`/Griffe ISC，均为**构建期依赖**、不进运行期 / 不进 wheel。
- 已定 · **生成物不入库（`site/`）**：`site/` 进 `.gitignore`（`REUSE.toml` 兜底声明）。
  事实源永远是 `docs/**`，站点只是它的一个投影——**不存在两份文档打架**。
- 已定 · **`nav` 即文档清单**：新页面必须在 `mkdocs.yml` 的 `nav` 登记；未登记页会被构建但隐身，
  `--strict` 不报错（这条靠自觉，写进 `rules/references/docs.md`）。
- 已定 · **`README.md` 只做稳定门面**：入口 + 定位 + 最短命令，**不复制**会长大的「现状 / 进度」
  （两处必然分叉；本任务就是来修这个债的）。细节一律链接到 `docs/`。
- 已定 · **权威顺序 = `路线图 > 设计 > 代码`**：路线图管「要什么」——做什么、按哪套设计、
  落在哪个版本；设计与代码往它收，冲突时以路线图为准。代码管「现在是什么」，是现状的唯一证据；

- 已定 · **文档站双语：中文是事实基础，英文是机器翻译的产物**（2026-10-10 作者定，已落地）：
  走 `mkdocs-static-i18n`（MIT，构建期依赖）的 **suffix 模式**——带 `.en` 后缀的是译文、
  不带后缀的归默认语言，故中文留在 `docs/**/*.md`、英文是 `docs/**/*.en.md`，
  线上是 `/`（中文）与 `/en/`（英文）。
  | 为什么中文是基础：**中文是作者亲手写的，英文是译过去的**——故"谁是事实源"不再需要每次判断，
  看扩展名即可。这也是一条正当的国际化：**产品对外可用英文，但作者用母语写作**。
  | 为什么默认语言也取中文：**默认语言必须是内容齐全的那一边**。`--strict` 的"nav 指向不存在的页"
  只在默认语言里判定，故取中文默认，英文侧由 `fallback_to_default` 兜底；把 `en` 设为默认，
  任何一个还没译的页都得先补英文占位页。英文读者的入口优先级由语言选择器的**第一项**承担。
  | 否掉了什么：① 只挂 `extra.alternate` 的选择器而不真译（它一个字都不翻译，
  等于两个死链接）；② 英文默认 + 占位页（占位页本身就是要维护的第二份文档）；
  ③ **让作者逐页手写英文**（作者明示 token 经不起，故英文一律走机翻，见下一条）。
  | 三条构建口径（都是实测得出的，别重新踩）：① 英文导航**只列已译页**，否则
  `fallback_to_default` 会把中文正文渲第二份 URL，`mkdocs-autorefs` 报"同一标识多个主 URL"
  （89 条）而 `--strict` 失败；② 故 `autorefs.resolve_closest: true` 必须开，让每个页面
  指回离自己最近的那一份；③ **`navigation.instant` 与语言选择器不兼容**，已撤掉。
  **2026-10-10 起 20 页全有英文，故英文导航与中文导航逐条对应**（两边分组与顺序相同）；
  ①那条规矩仍成立，只是要反过来用：**新页先落中文时不要急着往英文 nav 加**。
  | 后果：已译清单与判定在 `docs/reference/i18n-status.md`（双语）；`scripts/docgen.py` 仍写
  `docs/reference/config.md`（默认语言）；**改了中文页要重译英文页**，两边不得停在两版。
  | Git：见本次提交。
- 已定 · **英文译文由机器翻译产出（CI 侧）**（2026-10-10 作者定并落地）：
  底座是**阿里云机器翻译通用版**（`alimt` 2018-10-12 的 `TranslateGeneral`，RPC 风格、AK/SK 签名）；
  生成器在 `scripts/translate.py`，工作流在 `.github/workflows/translate.yml`。
  | **签名自己算，不引官方 SDK**（作者定）：RPC 签名就三步（HMAC-SHA1 + RFC3986 百分号编码），
  故用 `hmac`/`hashlib`/`urlopen` 直接发请求；**请求形状照 SDK 抄**（见下"第 ④ 条坑"）。
  否掉了 `alibabacloud-alimt20181012` SDK：它拖进三十来个传递依赖（v1.5.2 实测），
  且会被 `deptry` 正确地判为"dev 依赖被产品代码 import"与"用了传递依赖却没声明"——
  那两条规则本来是对的，**不该为了让一个开发脚本进来就放宽它们**。
  | 为什么选阿里云：**主账号每月 100 万字符免费**，超出 50 元/百万字符；QPS 50。
  本站中文原文约 9.5 万字符，全译一遍占免费额度不到 10%——**这条路的实际支出为 0**。
  作者口径：若能得赞助再考虑升级（换更大的模型 / 更好的译质）。
  | 一并否掉的底座：DeepL API（免费档已停售，Developer 档是一次性 100 万字符、不重置）、
  Google Cloud Translation（每月 50 万字符免费，也够用，但要走境外服务）、
  LibreTranslate 自托管容器（无 key，但中文技术文质量明显更低，且要占 CI 分钟与缓存）。
  **话模型（按 token 计费）一律不用**——那正是"玩不起"的那一类。
  | 三条实现约束（写在脚本里）：① **只译正文**——围栏代码块整块保留，行内代码 / 链接 / 图片 /
  裸 URL 先摘成占位符再放回；② **增量译，不从头来**——每次只处理"缺英文页"或"英文页落后"的页，
  已一致的页**一个字符都不送**（判据与 `--check` 同一套，故门禁报落后 = 生成器会去重译）；
  ③ 单次上限 5000 字符，故按行分段。
  | **持久化的语义**（作者 2026-10-10 追问"会不会每次从 0 翻"）：译文**进 `main` 才算落库**；
  `translate.yml` 补译后自动提交到独立 `i18n/…` 分支并开 PR，PR 一合那些 `.en.md`
  就是版本库里的事实，下一次运行直接跳过。**手写页**（无摘要行）默认不动，
  `--stamp` 只补摘要行、不重译正文。
  | 四条踩过的坑（**别重犯**）：① 占位符不能用数字字形——会被行内规则当成普通文本吞掉；
  ② 也不能用控制字符——`\x0a` 会被 `splitlines()` 当换行，一行断成两行。
  **私有区字符（`U+E000` 起）是唯一安全的选择。**
  ③ **判据里的 `Code` 要按字符串比**：本接口返回的是 `"Code": "200"`（`WordCount` 也是 `"2"`），
  按整数 `200` 比会把**拿到译文的成功响应**判成失败。同一个比较在探针与 `_translate` 里各写了一遍，
  线上红两次才把两份都揪出来——判据只写一处（`_succeeded`）。
  ④ **请求形状照官方 SDK：`POST` + 表单 body，`Signature` 按值编一次**（2026-10-10 作者
  要求"照 SDK 源码定，不要猜"之后定下的口径）。此前是 GET 把整段正文塞进查询串（最长一条请求行
  17 KB），并把 `Signature` 原样拼在 URL 末尾——base64 里的 `+` 到服务端被表单式解码还原成
  空格即验签失败；**这个坑只在签名恰好带 `+` 时发作**（约四分之一），故两个字符的探针常蒙对，
  一整页几十次调用必踩（run 37997198159 一页都没译成）。两条作法自此钉在
  `tests/core/test_translate.py` 里：**别再凭"上次能跑"改请求形状**。
  | 漂移防线：英文文件头记一条 `<!-- translation-source-hash: … -->`（中文原文摘要），
  `scripts/translate.py --check` 靠它判"英文是否落后"；该检查已进 `translate.yml` 的 `drift` job，
  **2026-10-10 20 页译完后从 `--report` 换回默认，已是真门禁**（过渡期跑报账模式是因为
  还有页没译，而门禁不能常年红）。**别改用 `continue-on-error`**：写在 step 上与 job 级都不改
  job 结论，实测两次仍报 failure。
  | **分支上怎么验这条路**：`translate.yml` 的 `workflow_dispatch` 有 `dry=true`——真调接口把
  整批译一遍，但不提交、不开 PR，故合并前就能把"补译"整条路走通（run 37998121787 即以此跑完
  14 页 / 64260 字符）。探针（`--probe`，只送两个字符）则跑在两处：`translate` job 里做花钱前的
  自检，以及 PR 上一个独立的 `probe` job（**限同仓库分支**，fork 的 PR 事件拿不到 secret）。
  **为什么单拉一个 job**：`translate` 在 PR 上被 `if` 跳过（它要建分支、开 PR），若探针只住在
  它里面，"请求装配改对了没有"在分支上就永远没有答案——只能等合并后在主干上第一次真跑，
  机翻那两次红都出自此。
  | 需要作者做的一次性设置：给一对**只授 `alimt:TranslateGeneral` 的 RAM AK**（别用主账号 AK），
  存仓库 secret `ALIBABA_CLOUD_ACCESS_KEY_ID` / `ALIBABA_CLOUD_ACCESS_KEY_SECRET`。
  | Git：见本次提交。
