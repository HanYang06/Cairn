# 内核规格（Kernel Spec）

> 本文件定义**内核的性质与职责边界**，不是实现说明。它是判定"某个设计该不该进内核、该放哪一层"的尺子。
> 与代码冲突时**以本文件的方向为准**；与本文件冲突的既有文档（见 §8）按 §8 处置。

状态：**v1.2 · M1–M3 已落地**（2026-09-22 立项：由「存储核心 + 通知」改为「对象主干 + 事件对象」；
v0.2 补：唯一引擎「信号处理器只解析包」、`Core`（门户 + 实例管理）、`Attr` 归工具单元；

## 1. 性质变更（这次要改的是什么）

**变更前（现状）**：内核是**存储中心制**。`Bucket` / `Block` 是立论起点，"上层一切最终都是块"；`core/signal` 是在存储事件（`ObjectPut` / `ObjectDeleted`）之上**补出来的通知层**。对象是被存的东西。

**变更后**：内核的主轴是**对象本身的生命周期**。存储退为四个模块之一，职责是"对象进得来、出得去"。信号是**门户**，工具单元负责**事件的创建与组合**，配置是被门户暴露的参数真源。

这不是"往上提一层"，是**换主轴**。存储实现本身**不做巨大改变**（见 §5），改的是它与其它三块的关系。

---

## 1.5 历史概念的处置（默认是删）

这次变更的性质决定了：**大量历史概念被重新定义，甚至没有容身之处**。这不是副作用，是目的——"都是对象"的写法一旦立起来，旧东西不是被兼容，而是不再需要。

**默认动作 = 删**。判据：

> 一个旧概念若无法映射到**这 5 个对象**（§2.6）里的某一个，或无法表达为**工具单元的标注**，它就**没有容身之处**，直接清理，不做兼容层、不留双写法。

因此**旧门户（现有 `core/signal` 的门户形态）直接清理、重新做一套**——不是在旧实现上改语义。凡"清理"与"改"有分歧，选清理。

---

## 2. 核心思路（唯一心智模型）

**完善的 OOP**：创建对象 → 对象进 → 对象出 → 获取对象 → 修改对象 → 传递对象。

这是内核的工作逻辑，也是它的路子。任何设计若不能落回这条线，就不属于内核。

判据：一条新机制若说不清它服务于这条线的哪一段，就不该进内核。

---

## 2.5 唯一引擎：信号处理器

抽象到底之后，内核的**逻辑只剩一件事**：

> **信号处理器 = 解析事件对象包。**
> 按包里的不同信息 → 产生不同的**调度决策 / 通信 / 反馈**。

这是本次设计的**收敛点**，也是"反而是简化了设计"的由来——不是功能变少，而是**逻辑只剩一处**。

约束：

1. 四个模块**本身不带逻辑**。它们只负责：让包产生（工具单元）、让包流动（信号门户）、让包能进能出（存储）、给出参数真源（配置）。
2. 处理器只**读包、决策**，不持有业务状态、不认识领域语义。
3. 一条新逻辑若无法表达为"对包的解析 + 在此基础上的决策"，就不该进内核；它应当表现为**新的包信息**或**新的工具单元**。

---

## 2.6 对象集合（少而硬）

内核的形态是**抽象 + 底层的混合**：先规定有哪几种对象、再约束它们的行为。**对象数量要少**——真正有效的对象不多，宁少不多。

**内核对象**（有实例、有状态、承载逻辑与生命周期）：

| 对象 | 定性 | 行为约束 |
|---|---|---|
| **`Core`** | 内核**核心门户** = 能力提供 + **对象实例管理** | 实例的唯一权威（持有、寻址、生命周期）；对外只经它取能力 |
| **`Signal`** | **事件处理器**＝§2.5 的唯一引擎 | 只解析包、只决策；不持业务状态、不认识领域 |
| **`Storage`** | 对象**进 / 出 / 找** | 见 §5；检索是可重建投影 |
| **`Conf`** | 参数**真源** | 经门户可达；**单向依赖 `conf → 无`**（存储读 conf，反过来不许） |

门户进来的是 **`Event`**（见 §4）；`Attr` 一类是**工具单元**（见 §6.5），不是内核对象。

**实现落点**（v1.2）：内核对象在 `core/kernel/`；**工具单元在 `core/tool/`**——两条路分开，
因为工具要被存储层在**导入期**使用，而门户依赖存储，二者不能同包（同包必成环）。

**分界线（可判）**：

> **工具单元**：静态标注，**无逻辑、无状态、不执行**，只供解析辅助 → 形态无所谓（对象 / 装饰器 / 类型皆可），能承载工具语义即可。
> **内核对象**：有实例、有状态、承载逻辑与生命周期。

新增内核对象须能回答：它承担的是**实例管理**还是**能力提供**；两者都不是，则不属内核。

> **为什么必须有实例管理**：`Core` 不只是能力的提供，它同时承担对象的实例管理。
> **如果连实例本身都管不到，信号与事件传递都是空谈**——这是本轮最硬的一条依赖。
> （对照现状：能力散在 `Vault` / `Domain.bind` / `Signal` 地址树上，"谁持有哪个实例"没有单一权威，于是句柄缓存钉死、`bind()` 之后信号发不出去这类问题才有生长空间。）

## 3. 内核构成

四个模块，一条主轴：

```
                 ┌──────────────── 门户 ────────────────┐   ← 逻辑只在这里
   Event ──────► │   Signal（事件处理器：只解析包）        │   （解析 Event → 决策）
                 │   Core （能力提供 + 对象实例管理）      │
                 └──┬──────────────┬──────────────┬──────┘
                    │              │              │
               Conf 配置      Storage 存储     工具单元
              （参数真源）    （对象进 / 出）   （Event 创建 / 组合）
                    └──────────────┴──────────────┘
                                   │
                        对象主干（创建→进→出→修改→传递）
```

| 模块 | 职责 | 明确不做 |
|---|---|---|
| **信号** = `Signal`（处理器）+ `Core`（门户） | `Signal` 是唯一引擎：**只解析包**；`Core` 提供能力 + **对象实例管理**；获取配置、存取对象、发起与传递事件都从这里过 | 不持业务状态、不替存储干活；**逻辑只在解析包**（§2.5） |
| **工具单元** | 承载工具语义的**静态标注 / 组合件**，服务于 `Event` 的创建与组合 | 无逻辑、无状态；不直接碰存储、不认识领域；**与 `ui_tools` 毫无关系** |
| **配置** = `Conf` | 内核配置的**唯一真源**，经门户可达 | 不做应用级配置（应用级归 App） |
| **存储** = `Storage` | 对象**进 / 出 / 找**（放得进、取得出、找得到；检索是可重建的**投影**） | 不发即时通知、不参与编排、不认识领域语义 |
| **`Event`**（门户入口，非模块） | 进来出去的都是它：自描述的事件包（§4） | 不进存储、不持久化 |

## 4. 事件对象（`Event`）

**事件是对象，不是通知。** 这是本次变更里最硬的一条。**从门户进来的就是 `Event`。**

**形态**：`Event` 以「**动作 + 行为描述**（+ 可能有的**承载体**）」完整描述一种事件的形态：

| 成分 | 作用 |
|---|---|
| **动作** | 要发生 / 已发生的是什么（动词） |
| **行为描述** | 该动作的形态与参数（怎么做、对谁、带什么条件） |
| **承载体**（可选） | 随事件一起走的东西（非对象的载荷，如字节 / 流） |

由此，`Event` 的性质**接近消息协议**：它是一段自描述的包，而不是一次函数调用。

**定性**：`Event` **不进存储**（不是持久化之物）。它只活在链路上：

- **(a) 单机**：内存里的一个**生命状态**——被创建、被传递、被解析，生命结束即消失；
- **(b) 网络**：以**数据流**形式传递；到达实际机体后**重新序列化回 `Event`**，继续以 (a) 的形态存在。

推论：

1. **自包含、可编解码**（否则 (b) 不成立），但**不被持久化**。任何"把事件写进库"的设计都超出内核。
2. **解析 → 决策是自然的一步**：包进来，处理器解析，据包内信息决定调度 / 通信 / 反馈（§2.5）。
3. `Event` 是**驱动**：链路因事件而推进，而不是因为某人直接调用某人。它驱动**对象**的变化；事件自己不是被管理的数据。
4. **对象实例不随包走**：包里给的是**目标的可辨识信息**，实例由 `Core` 的实例管理取出（§2.6）。否则 (b) 无法成立。

## 5. 存储的处置（最小变更）

**存储不做巨大改变。** 它本来该干的（放得进、取得出、找得到）是对的；要做的是**职责剥离 + 增量**：

| 动作 | 内容 |
|---|---|
| **剥离** | 把不属于"进 / 出"的职责从存储里拿出去：即时通知、编排、领域语义、被当作内核立论起点 |
| **剥离** | **对象与块分离**：对象是对象，块是存储的落盘单位，两者**不是同一个概念**，不靠"继承 `Block`"来定义身份 |
| **已剥离（M4a）** | **对象不再私藏门户引用**：`Block` 的门户归属是**显式字段** `core`（`attach` / `detach` / `attached`），不再是 `_vault` 私有字段；**落盘一律显式 `core.put(data)`**，领域侧不再有 `data.save()` 这种隐式落盘 |
| **增量** | 缺的能力按需补（压实 / GC / 迁移等工程债），**不借机重写** |

判定：如果一个改动能被描述为"存储内部实现的变化"，它**不该**引起其它三个模块的语义变化。

### 5.1 M4 剩余（卡口：版本装回哪儿）

> 2026-09-24 按代码核对：**版本能力当前整体缺失**，不是"两处直连待收口"。
> `VersionStore` 与 `core/storage/version.py` 已随内核重建移除；`feature/note/versions.py` 只剩
> `NoteCodec`（diff / apply / digest），**全库没有一处写版本表**；`Note` 服务只有 `save` / `persist`，
> 没有 `history` / `body_at` / `restore`（其 `save` 注释写着「版本由领域日后自建」）。

现存的两处存储接触：

1. **版本**：只剩 Codec（`feature/note/versions.py`），**存储侧没有**——待按 Q7 装回；
2. 领域表挂载：`relation` 表经 `core.storage.table`（`feature/shared/relation.py`）。

> ⛔ **待决（Q7）**：版本能力装回哪儿？
> **A · 存储能力**——`Storage` 提供版本能力（`versions(oid, codec)`），域只给 `Codec`；
> 代价是存储要认识"版本链"这个偏领域的概念。
> **B · 域自带**——域经门户拿一张属于自己的表，版本引擎留在域侧；
> 存储保持纯净，但域仍要经门户触到表。
> **两处证据当前不一致**：本规格倾向 A（链 / 顺序 / 回放 / 压实与领域无关，已是通用引擎；符合
> "同一事实只有一处"）；而 `Note.save` 的现存注释是"版本由领域日后自建"（倾向 B）。
> **裁定前不要按任一侧动手。** 定完即可收口 `core.storage.bucket` 的对外面。

## 6. 工具单元

工具单元 = 承载**工具语义**的静态单元，与信号配合使用。**形态不强制**：对象、装饰器、类型皆可，只要能承载工具语义。

- 它服务于 `Event` 的**创建与组合**（具体形态由 §9-Q1 / Q5 决定）。
- 它是**内核相关**的：实打实进 `core`。
- **与 `ui_tools` 毫无关系**：后者是脚手架性质的界面工具层（部件 / 布局 / 页面），只是名字里都有"工具"。

> ⛔ 未定（见 §9-Q1）：工具单元与现存 `@action` / `Topic` / `Domain` 的关系是**取代**还是**重建**。
> 一条硬约束先立在这里：**不允许"工具单元"与 `Action` / `Topic` 并排存在两套同类机制。**
> 本文档自己就是反例的教训——内核每遇到表达不了的需求就并排加一个机制，于是产生了"同一事实两个来源"的整类 bug。

---

## 6.5 工具单元的成员（少而硬）

工具单元里**东西不多，真正有效的对象不会特别多**。已识别的成员（**实现落点 `core/tool/`**）：

| 模块 | 成员 | 定性 |
|---|---|---|
| `core.tool.attr` | **`Attr` / `Data`** | **字段的高级标注工具**：静态标注、自身无逻辑，只供解析辅助 |
| `core.tool.action` | **`action` / `actions_of`** | **行动作的静态标注**：供解析器在登记时扫描成行动作表 |
| `core.tool.topic` | **`Topic`** | **多播事件的声明**：发出 / 订阅一律经门户 |
| — | `Event` 的创建 / 组合件 | 待识别（形态由 §9-Q5 决定） |

**为什么 `Attr` 归工具**：它**本质上不是存储的东西**。给字段做标注本来有两种等价写法——**用字段名标注**（`title: str = ""`），或用**类型来标注**（`title: Attr[str]`）。后者只是"高级"一点的标注手段，本身**不含任何逻辑**，属**静态解析**范畴。

推论：`Attr` 迁出存储**不是搬家，是归位**。顺带解掉一处长期别扭——`Attr` / `Data` 之所以看着像两个并列物，是因为**它们本来都不是存储的东西**。

> ⛔ 待定（见 §9-Q3）：`Data` 是否与 `Attr` 合并（同一个标注工具的两种用法），还是保留为独立成员。
> 现状：两者同机制、同存储，`Data` 仅作语义区分（"承载数据"vs"描述属性"）。

## 7. 判定标准

> **换实现不得改语义，不得改第二处。**
> 且：**一切跨模块行为必须能且只能经信号表达。**

补充可测的四条（任一不成立即判设计失败）：

1. **逻辑只有一处**：内核里出现的业务逻辑必须能归约为"解析事件对象包 + 决策"；出现第二个"做判断"的地方即失败。
2. **加一个领域，`core` 不新增概念**（只加值 / 只加声明）；出现新机制或新类型分支即失败。
3. **换一种实现**（存储形态 / 编码 / 缓存策略），允许改的只有该实现的所在处；出现"另一处也得跟着改"即失败。
4. **没有两套同类机制产出同一类事实**；出现"两种写法并存"即失败（包括为了兼容而保留的旧写法）。

## 9. 结论与遗留

### 9.1 已定（M0–M3）

| # | 问题 | 结论 |
