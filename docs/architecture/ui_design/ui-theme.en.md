## 1. Objectives and Constraints

-**Aesthetics:** Prioritize light colors (note-taking and project management primarily involve reading and writing; see §3.1), ample white space, and restrained animations.
In harmony with the brand’s colors (cool gray, warm ochre, and moss green). **Dark mode is optional**, can follow the system settings, and can be manually overridden.
-**Controllable**: The appearance is derived solely from the token; it does not introduce any heavy frameworks that could compromise the license (especially in the frontend ecosystem—see §4).
-**Fast**: The capture surface (hotkey) must be instantly available, without any delay caused by front-end startup.
-**Maintainable**: The theme’s styles are centrally managed using **tokens**, rather than being scattered across individual components.

## 2. Token: The Sole Authentic Source of Appearance

Components should only reference tokens; hardcoding colors, spacing, or border radii within components is prohibited. Tokens are divided into five categories:

| Category | Content | Value |
|---|---|---|
| **Color** | Background/Panel/Border/Text/Accent/State | See §3 (light and dark variants) |
| **Rounded Corners** | `xs` / `sm` / `DEFAULT` / `lg` / `xl` | 3 / 6 / 8 / 10 / 12 |
| **Spacing** | `xs` / `sm` / `md` / `lg` / `xl` | 4 / 8 / 12 / 16 / 24 |
| **Text** | Font stack/Font size/Line height | See §3.2, §3.7 |
| **Animation** | `instant` / `fast` / `base` / `slow` | 0 / 120 / 180 / 260 ms |

-**One set of tokens, two sets of values** (dark/light): The component only references the tokens; switching themes simply changes the values.
-**Whitespace first**; accent colors are used sparingly, reserved only for selected states, links, and primary buttons.
-**Animations should be functional only** (e.g., fade-in, translation), avoiding purely decorative effects; provide a “Reduce Animations” toggle (§6.7).
The maximum duration for interactive feedback is specified in §3.5; shadows and rounded corners are covered in §3.3 (frozen).

**Light Mode Preferred (2026-09-30, Author’s Decision)**: Previously, this document treated dark mode as the default, but the rationale was never documented; therefore, it has been reversed to align with user demand.

1. **The product’s core identity should align with what it does**: Cairn is all about **project management and note-taking**—the total time spent reading and writing takes precedence above everything else.
For comparable industries: Note-taking and writing tools use a light theme by default, with a dark theme as an **optional setting**; terminals and code editors, on the other hand, typically have dark mode as their default.
2. **Do not choose pure white paper**: Its brightness is approximately 8.5% lower than that of pure white—just enough to reduce glare without appearing overly yellow.
Thus, the on-screen hierarchy forms **three levels of lightness**: the paper (workspace background) → the panel (white, for content) → the overlay (white + shadow).
The main text scores **14.52** on paper and **15.80** on the panel, both significantly exceeding AA.
3. **Dark mode remains an optional setting**, which can follow the system or be manually overridden (via the “Display” entry in §6).
4. **Both sets are first-class citizens**: The generator ensures that the two sets of keys are exactly identical, assert.
**The main text and the accent color both meet AA accessibility standards against their respective backgrounds**—adding a color means it has to pass accessibility review.

**Why the accent color is warm gold (supported by evidence, not just a matter of feel)**:

1. **The stone is cold**: Use per-pixel color sampling; for the dark areas of the stone.
(R−B = −11), light-receiving stone (R−B = −18) -- **neutral colors are inherently cool gray-blue**;
The current one is in the same family as it, **so the dark background remains unchanged**.
2. **Light is warm**: The only warm color in the logo is where sunlight grazes the stone ridges (R−B = **140**).
**The accent color has been changed from cool blue to warm gold**—a cool stone, with a warm glow that mirrors the logo’s structure;
In contrast between warmth and cold, the golden hue naturally becomes the sole source of light in the scene. **The tension arises from this; it doesn’t depend on warming up the base color.****
3. **One color value, one sample**: Dark color `#EDB761` (with contrast ratio **10.41**)、
Light color `#8A5F22`(against `#F7F5F2` **5.16**)--all meet WCAG AA;
The original gold content on a light-colored base is only 1.82, **so no original gold is needed for light colors**.
4. **Neutral colors still follow GitHub Primer**; and retain `borderFaint` / `faint` / `hover`/
With high-contrast overlay (§6.7).
5. **Text hierarchy at Level 3**: Main text/Secondary/Weak, with approximate font sizes of 14.5 / 5.9 / 4.2 when using lighter colors—
This is where the interface’s sense of “depth” comes from—without relying on borders.
6. **Deliberately blurred boundaries**: The contrast with a base of only 1.34–1.46—**boundaries should not be the focus**,
Recognition relies on negative space and tonal layering; use accents where emphasis is needed.

**To be determined**: A light-colored version of the brand mark (the logo features a dark background with warm lighting; under a light color theme, a reverse or outlined version will be required).

### 3.3 Shadows and Rounded Corners (**Frozen**)

Caliber (2026-09-30): **Shadows and rounded corners have been frozen; any subsequent changes will be made solely according to the three mechanisms listed below.****
Both manage the common visual appearance of **all components**, with **stability taking precedence over minor visual enhancements**.

**Key takeaway:** Don’t exaggerate or be lax, but the softness must be visible and palpable.**

| Criterion | Implementation |
|---|---|
| **No Exaggeration** | Shadows must not obscure the content (in the proofread draft, this corresponds to the “too heavy” setting on the reverse side) |
| **For Softness** | **Two Layers**: On the layer with the small offset, trace the edges; on the layer with the large blur, add softness—this can’t be achieved with a single layer (if you want softness, it gets blurry; if you want sharpness, it becomes stiff). |
| **Can be seen** | “Soft” refers to **softness that can be perceived**; if it’s so soft that it’s invisible, then it might as well not exist (“too flat”—that extreme is the opposite.) |
| **Rounded corners shouldn’t be too sharp** | Rounded corners **scale with the size**: Whether they’re soft enough depends not only on the value but also on the **ratio to the element’s dimensions**—3px on a large card still looks sharp. |

> **Why "hard" should be avoided (a reusable design principle)**:
> Flat shading/hard edges were introduced back then because **rendering capabilities were simply limited to that** (according to the developer: “We really didn’t have that technology at the time”).
> Therefore, the criterion is: **Any visual convention that was deemed “the only way back then” should be updated once the technology has matured; failing to do so results in a negative score.**
It will be interpreted as “not done” or “retro.” This principle can be extended to similar practices such as hard edges, solid color blocks, and stateless transitions.

**Shadow values (only three levels, with darker shades using an even darker black)**:

| Token | Used For |
|---|---|
| `--shadow-sm` | Hover, Pull-down, Tooltip |
| `--shadow` | Pop-up, Menu, Command Panel |
| `--shadow-lg` | Modal, independent window, card being dragged |

See the values in `config/theme/tokens.json` (double layer: one layer with a small offset along the edge, one layer with a large blur).
**Shadows in dark mode must be heavier than those in light mode**—the new version uses this rule for shadow values (the old one was barely visible on dark backgrounds).

**Rounded corner values (five levels, assigned by "hierarchy," not by "aesthetics")**:

| Token | Value | Used In |
|---|---|---|
| `--radius-xs` | 3px | Tags, subscripts, selected indicator bar |
| `--radius-sm` | 6px | Bottom padding for small buttons, input fields, and list items on hover |
| `--radius` | 8px | Panels, cards, buttons |
| `--radius-lg` | 10px | Overlay, Menu, Popup |
| `--radius-xl` | 12px | Cards and modals in the card workspace |

**Rule:** **Outer radius ≥ Inner radius** (when nesting, the inner layer cannot be rounder than the outer layer); otherwise, the nesting hierarchy will appear visually inverted.

**Standardization (supplemented on 2026-10-10; both count as the "hard" opposite)**:

1. **Only one left margin at the same level**: Within a single container, the left edges of section titles, list items, and sub-items must align in the same column.
Indentation should be expressed using the phrase “which element does this belong to” (e.g., a section title governs a group, and its sub-items belong to it); **do not** use “move the text further to the right/left.”
"Several pixels" expression. Quantifiable criterion: The left-edge deviation of each text layer should be 0 (see the measured values on the document-side for details below).
2. **Levels are indicated by structure, not by numerical values**: When the parent item is only a section title and the child item is the actual link, the left edges of their text align.
Levels are distinguished by grouping spacing and font weight (in the same family as “outer radius ≥ inner radius” — hierarchy is expressed through structure).

The origin of this feature (**I’ve encountered it twice, so I’m noting down the implementation as well**): When adding a hover capsule to the sidebar of the documentation site,
The first version added horizontal padding to `.md-nav__link`—which altered the box model, causing the previously well-aligned layers of Material Design to become misaligned.
(Actual measurement: section title `x=16`, sub-item `x=8`); in the second edition, a negative outer margin was applied to the sub-items again, but in the opposite direction.
It has become a sub-item that is even further to the left than the section title.
The correct solution is to keep the text fixed and only expand the background outward: set its horizontal padding to zero.
Use an equal negative margin to push the hover background color beyond the left edge. Therefore, when modifying the sidebar style, **measure x first before making any changes**.
Don’t use “looks about right” as the deciding criterion.

**The three rules of the freeze mechanism (how to add, not "don't move")**:

1. **Gear positions only increase, never change**: When a new component cannot fit into the existing gear, **add an additional gear**; **leave the original gears unchanged**—
Once the old settings are changed, the visual appearance of the entire stack shifts accordingly.
2. **Changes must be supported by functional evidence**: Visual preference doesn’t count; **contrast fails to meet the standard, and shadows are indeed invisible in certain scenarios**.
Only this kind counts. Record the changes in this document and in the change history.
3. **Test values must not be entered into the token**: During the exploration phase, you can experiment freely, but **you must not insert `config/theme/tokens.json`**;
Only enter once it’s decided. Avoid allowing the token table to serve as a draft entry, where entries accumulate without a clear way to determine which one is active.

Proof copy (three levels of shading, both sides; rounded corners proportional to the size): `.design-lab/comp.html`(not to be filed).

### 3.4 Button and Action Hierarchy (Capsule Boundaries)

The author favors **capsule buttons**; they should be implemented as a bounded pattern, otherwise they will be overused across all scenarios.

| Level | Form | Where Used | Number per Screen |
|---|---|---|---|
| **Main Operation** | Capsule · Solid (`accent` Bottom `accentText`) | Save, New, Confirm | **Up to 1** |
| **Sub-operations** | Capsule · Ghost (only appears at the bottom when there is no bottom, or when hovering) | Command ribbon, toolbar | Unlimited |
| **Irreversible Operation** | Capsule · Text | Permanently Delete, Empty | Nearby |
| **List/Menu Item** | **Rectangle** (`radius-sm`) | List row, right-click menu item | - |
| **Container Type** | **Rectangle** (API level 26 and above) | Card, Panel, Input Field | - |

**Criterion in a nutshell**: Actions can be capsules, but containers are not capsules.**
The trade-off is that the row height increases, and fewer actions can be displayed on the same screen—**this is an expected consequence** (see the single-action principle in §3.5).
Icon buttons are also round, but **must include a hover tooltip** (§6.11).

### 3.5 Single Actions and Animation Limits (Author’s Definition)

UI isn’t better the more complex it is, and more colors don’t necessarily make it better; clarity, simplicity, and a single, focused action are all that’s needed.**
The more UI interactions there are, the uglier it becomes.**

From these three points:

1. **One main operation per screen** (as stipulated in §3.4), with all others rendered as ghosted elements or moved into the right-click menu.
**If it can be accessed via the right-click menu, don’t move it to the main interface.**
2. **No in-between animations**: Transitions are direct—no intermediate steps (no cutscenes, no narrative-style transitions).
The rationale is based on the author’s judgment: **coherent animation requires narrative support, whereas the UI itself cannot carry a narrative.**
Thus, the only remaining costs in the intermediate process are bandwidth and latency.
3. **Maximum duration for interactive feedback = `--dur-base`(180ms)**: Use `fast` or `base` for hover/press/unfold;
(260ms) Only expand or collapse elements with "large displacement".
**Hover and selection are both instantaneous** (no color transitions are used to prevent adjacent items from cross-fading into each other, which could be perceived as two items being highlighted simultaneously; §6).

**The only exception**: splash screens and progress feedback—they are **states**, not narrative.

### 3.8 Font Replacement Mechanism (Scope: Does Not Lock to a Single Set)

Specification (2026-09-30): **The font is not locked to a specific set—tokens serve as font mappings, allowing users to replace them at will.****
A set is provided by default; **users can choose from the fonts already available in the system**--
**These fonts are provided by the user’s system and are unrelated to this repository; the copyright responsibility does not lie with this repository.**

**The boundaries of this inference must be clearly defined; otherwise, the responsibility will revert to this repository**:

| Method | Who is distributing the font | Copyright liability |
|---|---|---|
| **Bundled**: Fonts are distributed with the installer | This repository | **Borne by this repository** (must be OFL‑licensed or otherwise explicitly permitted for bundling) |
| **Use system font** (just the font name) | Operating System/User | **Not in this repository**—this is the current solution |
| **Enumerate system fonts and list their names**, for the user to choose from | Still relies on the system | **Not in this repository**: Only reports "what is installed"; does not provide, copy, or cache |
| The app **selects and automatically replaces** fonts on behalf of the user with a specific commercial font | System | **Not applicable**: If the app selects the font on behalf of the user, it constitutes guidance, and the responsibility reverts to this repository |

**The red line of this mechanism**: The application only provides the **name** and the **replacement action**; it does not make selections on behalf of the user, nor does it copy font files.

**Three layers, each layer can be applied independently** (see character descriptions above):

```
--font-sans  界面   ← 默认：system-ui → 思源黑体系
--font-mono  编辑   ← 默认：Sarasa Mono SC / Cascadia / Consolas 链
--font-read  阅读   ← 默认：system-ui → 思源黑体系
```

**Mechanism form (consistent with the token mechanism, without adding a second chain)**: Tokens are, by nature, CSS custom properties.
Therefore, user coverage simply involves overwriting these variables on the platform—without adding any new build steps or creating themed modules.

-**Storage**: User choices are stored in **application-level settings** (similar to the cardboard layout; as per Memory’s “Frontend Design” §3, they are not saved in the database).
-**Applicable Scope**: Global (one value for each of the three layers); no "component-specific font assignment" is performed.
-**Method of application**:.
-**Default user relationship**: Follows the existing policy of the configuration engine—**values modified by the user are not overwritten by default values**.
By default, it is only applied to the "unmodified" layer. Therefore, when the default font is upgraded or replaced, any previously modified settings remain unaffected.
-Ligatures are assigned default values along with the default font, as specified by the "font package" convention.

**Precautions for all areas**:

1. **Font existence must be checked**: If a non-existent font name is specified, the system will **silently revert**.
The interface shows no changes, and users have no way of knowing why. Therefore, a check is needed to determine whether “the font is available on this machine.”
2. **Enumerating system fonts must be handled by the shell**: The frontend does not have this capability and must rely on the shell to provide it. A viable implementation has been verified—

(**MIT**,`get_system_fonts() -> Vec<SystemFont>`).
**This pertains to window and system capabilities and does not constitute a business entry shell** (see criterion in §1).
3. **Proportional spacing is determined by the actual measured character widths, not by the font’s design**: Some Chinese fonts include Latin characters with fixed (monospaced) widths, but **Chinese characters are not uniformly spaced**.
Whether a font is suitable for use as a monospaced font must be determined by the **actual measured character widths** (including CJK characters); it cannot be decided solely by whether the name contains `Mono`.
4. **A revert path must be provided after changes**: Each character must have a “restore default” action; otherwise, if the user makes a mistake, the only option will be to delete the configuration.

### 3.9 Criteria for "Non-Floral" Interface Fonts (Author’s Definition)

Font size (as of 2026-09-30): **For text outside the editable area, monospacing is not required; visual appeal takes precedence.**
Decorations/ornamental fonts are strictly prohibited from appearing in the interface.**

This is not a matter of aesthetic preference: the distinguishing features of script fonts come from their ornamental stroke forms, but at small sizes—11 to 14 pixels—these decorations tend to degrade into visual noise.**
A more fundamental reason is the same as in §6.13: **the glyph should match the function of the text**.

**Therefore, the typographic criteria are divided into three levels based on "the role of text within the interface":**

| Role | Example | What the font should do |
|---|---|---|
| **Background Color** | Labels, Lists, Buttons, Metadata, Status | **Least Obtrusive**: Neutral Sans-Serif Font, High Character Density, Uniform Stroke Width |
| **Element** | Note body, card title | May have distinguishing features, **but must remain legible at 14px or smaller** |
| **Embellishment** | Empty-state title, display state | Can have personality, **but must not be mere decoration/Script-style fonts** |

> **One-Vote Veto (Decorative/Script Fonts)**: Handwritten fonts, calligraphic fonts, artistic typefaces, and “design-oriented” fonts featuring decorative strokes—
These are **only for the logo/brand materials** and will not be included in the interface. The criterion is “whether it blooms,” not “which manufacturer.”
>
> **Division of responsibilities with §6.13**: §6.13 handles the “**layer**” (the interface layer should not use fonts such as Song or Kai that are primarily for **reading**),
This section deals with “**flowers**” (decorative types are not used at all), and two criteria operate in parallel. First pass the "layer," then pass the "flower."**

### 6.13 Editor Body (Line = Paragraph)

The editor renders line by line; each line constitutes a paragraph, with character-level styles applied within the inline range and paragraph-level attributes applied to the paragraph element.
(See §5.1; **this page is pending rewrite and is currently not in the repository**).

-**Soft line break**: Automatically wraps lines when the equivalent Chinese text is 300 characters or fewer.
-**Extra-long line**:> 300 characters (threshold is `OVERLONG_WEIGHT`, **constant to be determined**: not yet implemented in the code) → No line breaks; this line can be **horizontally scrolled**.
(Authors are required to manually insert line breaks); in the blank space at the bottom right of the editor, an **“End of Line” button** appears. Click it to move the cursor to the end of the line and scroll all the way to the right.
Does not automatically split; does not display prompts.
-**Paragraph Properties** (alignment/heading/list/indentation/quote/code) rendered inline: headings adjust font size and weight,
List **serial number derivation**, with left-aligned references, monospaced code blocks, and a background color; no line breaks.

> **Frontend Implementation Tip**: The "one line per paragraph" approach in this section is **isomorphic** to the frontend rich-text editor's **block-based document model**.
It is the primary criterion for model selection; the license should be verified concurrently during the selection process.

**Criteria for not using Song or Kai fonts in the UI layer (supplemented on 2026-09-30)**: The issue does not lie in the typeface itself, but in the **mismatch between the placement and the text’s function**.
This is not a matter of aesthetics; there are three specific reasons:

1. **They are characters meant to be “read,” not “scanned”:** Song typeface and regular script were designed for **continuous long texts**, featuring thin strokes, strong contrast between thick and thin strokes, and a low character‑occupancy ratio;
Interface text—short, scannable strings such as labels, buttons, and status messages—appears blurry when rendered at 11–14 px.
2. **Numbers and Latin characters do not align**: The interface uses a mix of Chinese, English, and numbers (for time, counts, and paths), but the Latin portion in Song or Kai fonts only offers one selection option.
Misalignment; monospaced fonts and Heiti fonts have a natural advantage in this regard.
3. **Register misalignment**: Kaishu script inherently carries a “handwritten/elegant” **narrative register**. Interface text is **functional**.
Using regular script is like giving functional text a narrative tone—**for the same reason as in §3.5, “Do Not Create Process Animations”**:
The UI does not carry narrative, so it does not adopt a narrative-style design.

> **Extrapolation**: This rule belongs to the same family as §3.3’s “Back then, that was the only way”—**if form and usage don’t match, it’s a negative point**.
> **Permitted exceptions**: For “read/display mode” (long-form, read-only content), serif or regular script fonts may be considered, as this mode is optimized for reading.
> Thus, the `--font-read` character came into being; it is **not used in the interface**.

### 6.14 Formatting Toolbar (Two Rows)

Two lines below the tab: **first line for character-level, second line for paragraph-level**. The layout is driven by the tool registry (data); **the positions are not hardcoded**.
