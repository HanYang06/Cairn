# 网络层（P2P 底层）规格

> 承接 [`storage-design.md`](./storage-design.md)（块 / 载体 / hub / 索引库）与 [`access.md`](./access.md)（传输加密 / 档位）。
> 定位：**网络是增强层，不是本体**。本地始终可用；联网使各节点持有的副本可以互相交换。

状态：**草案 v0.2**（未实现；已按「无 manifest、内容按 `checksum` 寻址」修订术语，落地前整体复核）

> **2026-09-19**：**未实现**的预留设计；原实验顶层包 `src/net` / `src/server` 已删除，落地时重设。
> 存储层已就绪（内容寻址），本层负责节点之间的内容交换。

---

## 1. 分层视图

```
应用/服务层      同步、博客、社区治理        ← 上层（未启动）
────────────────────────────────────────
数据面协议       want / meta / block          ← 本文件核心
节点角色         server（中心化·联邦共享） · peer（去中心化）
传输 / 安全      py-libp2p + Noise/TLS         ← 预留
发现 / NAT       mDNS · bootstrap · DHT · AutoNAT · Relay v2 · DCUtR   ← 预留
编址             checksum(内容) · id(块身份)
身份             传输身份 Ed25519 + X25519     ← 预留（未来引入）
存储             块 / 载体 / hub / 索引库       ← 已有
```

除「存储」行外均为**预留**：`py-libp2p` 未引入（`uv.lock` 无此依赖），传输、发现与身份三行不作为实现依据。

存储层已具备内容寻址：请求方给出一组内容摘要，应答方核对本地是否有对应记录。该问答是本层的最小原语。

## 2. 编址

| 目标 | 地址 |
|---|---|
| 内容 | `checksum`——内容地址，即 ID 摘要形态 `value_hash`（`sha256` 十六进制，`storage-design.md` §3.2），本库内容池去重键 |
| 块身份 | `id`——ID 对象的两套凭证：`value_uuid`（`uuid4`）与 `value_hash`（`sha256`） |
| 对端 | libp2p `PeerID`（由传输身份公钥派生；传输身份预留，见 §4） |

- 内容寻址使任意节点都能提供任意内容，无需中心目录。
- 对象的位置由索引给出，指向关系为 `块 id → body_ref → 内容记录`：`body_ref` 是块载荷里的保留键，携带指向内容记录的两套凭证（`storage-design.md` §3.2 / §5.3）。分享策略决定**谁可请求、谁可提供**。

## 3. 数据面协议（草案）

最小、面向流、可校验。协议 ID 前缀 `cairn/1`：

| 协议 | 方向 | 作用 |
|---|---|---|
| `/cairn/1/want` | 请求方 → 提供方 | 发一组缺失 `checksum`，请求内容 |
| `/cairn/1/block` | 双向 | 传块内容（远端可加密，逐块可校验） |
| `/cairn/1/meta` | 请求方 → 提供方 | 取块行元信息（`id` / `type` / `checksum`） |
| `/cairn/1/announce` | 双向 | 公告「我有哪些 id」（可选，走 GossipSub） |

流程（**pull 为主**）：

```
A: meta(id)            → 拿到块行（type / checksum）
A:  核对作者与签名（预留：签名能力未实现）
A: want([本地缺失的 checksum...])
                       → B: block(逐块流式回传)
A:  逐块：checksum 重算校验 → 写入 hub / 载体
```

- **对象即流**：大内容由分片块 + 索引块构成，可分段、并行、断点续传。
- **增量**：按内容哈希只传本地缺失的块。
- **校验**：逐块 `checksum` 重算；块签名**预留**（签名能力未实现）。版本链归领域层，不进存储与本层（`storage-design.md` §9.1）。

## 4. 传输 / 安全

- 传输：`py-libp2p`（QUIC / TCP / WebSocket）——预留，未引入。
- 信道加密：Noise / TLS（libp2p 内建）+ 传输 / 远端副本的 AEAD（本地不加密，见 `access.md`）；随传输实现一并落地。
- 身份：传输身份 Ed25519 / X25519（未来引入），PeerID 由公钥派生。
- 信任：块签名**预留**（签名能力未实现）；内容寻址只在明文 / 密钥可见范围内泄漏相等性（`access.md` §2）。

## 5. 发现 / NAT

| 场景 | 机制 |
|---|---|
| 同局域网 | **mDNS** |
| 广域网引导 | bootstrap 节点 / rendezvous |
| 大规模路由 | **Kad-DHT** |
| 可达性探测 | **AutoNAT** |
| 直连失败兜底 | **Circuit Relay v2** |
| 打洞升级 | **DCUtR** |
| 公告/订阅 | **GossipSub** |

对称 NAT 下打洞常失败，此情形必须回退到中继；该结果由 NAT 的行为决定，与实现无关。

## 7. Server 与 P2P 的关系（优先级）

```
Server（中心化 · 联邦共享）  —— 更底层、优先级更高
   │  天然携带公网节点
   ▼
P2P（去中心化）              —— 由 server 衍生
   └─ relay / bootstrap / 打洞协调 直接复用 server 的公网节点（无额外自建成本）
```

- **server 是基础通信**：中心化，但**联邦共享**（多个 server 可互通）。
- **P2P 是衍生**：去中心化，但**不自建打洞节点**——server 的公网节点兼任 relay/bootstrap/rendezvous。
- **共同前提**：两者的同一基础是节点互联与数据面通信。
- 结论：**server 优先级 ≥ P2P；先做互联与 server，再做 P2P。**

## 8. 分阶段实现

| 阶段 | 目标 | 依赖 |
|---|---|---|
| **P0** | 单节点 server：能被连、按 `want/block` 提供块 | 存储层（已就绪） |
| **P1** | 两节点互联同步：head 拉取 + 权限档过滤 | access 档位设计（预留，未实现） |
| **P2** | server 作公网节点：bootstrap / Relay / AutoNAT | py-libp2p（预留，未引入） |
| **P3** | P2P 打洞（DCUtR），复用 server 公网节点 | P2 |
| **P4** | 公告/发现：GossipSub + DHT | P3 |

P0 的范围限于单节点：不接触公网与 NAT，只验证「内容寻址 + want-list + 互联」这条最小链路。

## 9. 隐私边界

- 默认不广播本地持有的清单，仅响应请求。
- 元数据（谁连谁、传多少、何时）仍会泄漏；如需隐藏，须引入 PIR / 洋葱路由，不在本阶段。
- 档位决定可提供范围：私密不对外，公共仅限成员，公开可全网。
